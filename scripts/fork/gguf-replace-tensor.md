# gguf-replace-tensor.mjs: таблица n-грамм из полной модели

[gguf-replace-tensor.mjs](gguf-replace-tensor.mjs) делает копию квантованной модели, в которой один тензор взят из
другой модели. Написан для таблицы n-грамм Qwen3.8-Flash-Next (`per_layer_token_embd.weight`): в UD-Q4_K_XL она
лежит в IQ4_NL (90 байт на строку, 26.8 ГиБ), а из полной модели её можно взять без квантования или в q8_0.
Все остальные тензоры и метаданные остаются побайтно теми же, что в исходном кванте.

Таблица не грузится в память: кеш строк читает её с диска (`-lzm dio`), поэтому более точная таблица стоит только
места на диске, RAM и VRAM она не занимает.

## Что нужно

- node 18+ или bun. Пакеты не нужны.
- Полная модель (например, BF16 GGUF от unsloth) и текущий квант. Обе могут быть разбиты на части
  (`<имя>-0000N-of-0000M.gguf`): скрипт сам находит часть с тензором.
- Место на диске под новую часть (таблица ниже). Папка для результата должна быть на том же диске, что и текущий
  квант, тогда остальные части встают жёсткими ссылками и места не занимают. На другом диске они копируются.

| Вариант (`--type`) | Таблица | Новая часть больше старой на | Время сверх копирования |
| --- | --- | --- | --- |
| `keep` (тип полной модели, у BF16 это bf16) | 95.4 ГиБ | 68.6 ГиБ | нет |
| `q8_0` | 50.6 ГиБ | 23.8 ГиБ | ~8-9 мин под node, под bun вдвое дольше |

`--type bf16` переводит в bf16 таблицу полной модели в f16 или f32. `q8_0` и `bf16` дают те же байты, что
llama-quantize.

## Шаги

Команды из корня репозитория, в `cmd`. Пути примерные.

1. Посмотреть, в каком типе таблица лежит в полной модели:

   ```
   node scripts\fork\gguf-replace-tensor.mjs --list D:\models\full\Qwen3.8-Flash-Next-BF16-00001-of-00008.gguf per_layer
   ```

   Для каждой части печатается ее заголовок, для части с таблицей еще и строка вида
   `per_layer_token_embd.weight  bf16  [160, 320000xxx]  97656.2 MiB`. Тот же `--list` на файле текущего кванта
   покажет `iq4_nl`.

2. Пробный прогон: найти таблицу в обеих моделях, сверить строки, напечатать план, ничего не записать:

   ```
   node scripts\fork\gguf-replace-tensor.mjs ^
        --src D:\models\full\Qwen3.8-Flash-Next-BF16-00001-of-00008.gguf ^
        --dst C:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf ^
        --out C:\models\q4xl-ple-bf16 --dry-run
   ```

   В выводе должна быть строка `row check, 256 rows: correlation mean 0.99..`. Это сверка случайных строк старой
   (IQ4_NL) и новой таблицы. Если среднее ниже 0.9, скрипт останавливается: у таблиц разный порядок строк, то есть
   модели не от одного чекпойнта или конвертированы по-разному.

3. Записать: та же команда без `--dry-run`. Для 8-битной таблицы `--type q8_0` и другая папка:

   ```
   node scripts\fork\gguf-replace-tensor.mjs --src ... --dst ... --out C:\models\q4xl-ple-q8 --type q8_0
   ```

   Раз в 5 секунд печатается прогресс (ГиБ, МиБ/с, сколько осталось). Новая часть пишется во временный файл
   `.part` и переименовывается только после записи. Затем скрипт перечитывает её: имена, типы, выравнивание тензоров
   и несколько строк таблицы против полной модели. В конце ставит ссылки на остальные части и печатает путь для `-m`.

4. Запуск модели: `-m C:\models\q4xl-ple-bf16\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf`, остальные ключи
   те же. В логе сервера строка `table stays on disk ... blocks of 320 B` (bf16) или `blocks of 170 B` (q8_0) вместо
   `90 B` показывает, что читается новая таблица. Для харнесса это `MODEL` в `_local.bat` или аргумент `-m` в плече.

## Перенос на второй ПК

Части, кроме той, где таблица, у нового варианта те же, что у текущего кванта. Копировать нужно только новую часть
(`...-00002-of-00004.gguf`). На втором ПК положите её в новую папку и сделайте в этой папке жёсткие ссылки на свои
части 1, 3 и 4:

```
mklink /H C:\models\q4xl-ple-bf16\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf C:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf
mklink /H C:\models\q4xl-ple-bf16\Qwen3.8-Flash-Next-UD-Q4_K_XL-00003-of-00004.gguf C:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00003-of-00004.gguf
mklink /H C:\models\q4xl-ple-bf16\Qwen3.8-Flash-Next-UD-Q4_K_XL-00004-of-00004.gguf C:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00004-of-00004.gguf
```

Это работает, только если файлы кванта на обоих ПК одинаковые (одна и та же загрузка). Проверить можно хотя бы по
размерам файлов.

## Все ключи

| Ключ | Что делает |
| --- | --- |
| `--src <файл>` | любой файл модели, из которой берется тензор (полная модель) |
| `--dst <файл>` | любой файл модели, в которую он вставляется (текущий квант) |
| `--out <папка>` | папка нового варианта, не папка `--dst` |
| `--tensor <имя>` | тензор, по умолчанию `per_layer_token_embd.weight` |
| `--type keep\|bf16\|q8_0` | тип тензора в результате, по умолчанию как в `--src` |
| `--check-rows N` | сколько строк сверить перед записью (256), 0 - не сверять |
| `--no-others` | записать только часть с тензором, без ссылок на остальные |
| `--dry-run` | только проверки и план |
| `--force` | писать, даже если строки не сошлись |
| `--list <файл> [regex]` | тензоры файла (всех частей) с типами и размерами |

## Ошибки

- `the shapes differ` - у тензора разная форма в двух моделях: это другие модели.
- `the rows of --src and --dst do not match` - форма та же, строки другие (см. шаг 2).
- `needs N GiB, M GiB are free there` - не хватает места в `--out`.
- `<файл> exists, remove it first` - в `--out` уже есть новая часть от прошлого запуска.
- `split files are missing` - у модели не хватает частей рядом с указанным файлом.
- `no hard link for ...` - не ошибка: `--out` на другом диске, остальные части копируются.

## Проверено

На тестовой qwen4exp (модели разбиты на части, таблица не в первой): вариант с таблицей bf16 побайтно совпадает с
моделью, которую собрал llama-quantize с той же таблицей (98 тензоров из 98); перевод в q8_0 и bf16 дает те же байты,
что llama-quantize; остальные тензоры не тронуты; модели грузятся, в том числе с чтением таблицы с диска
(`-lzm dio`); таблицу с переставленными строками сверка останавливает (корреляция -0.01 против 0.997).

## Зачем

Таблица n-грамм хранит готовые сочетания токенов: имена, устойчивые обороты, редкие слова. Есть опасение, что 4-битная
таблица теряет именно редкое (малые языки, детали), что не видно на английском тексте. Официальные FP8- и NVFP4-кванты
держат таблицу в 8 битах. Проверка: KLD текущего кванта и варианта q8_0 против варианта bf16 на тексте нужного языка
(03, лучше на 395, где повтор дает KLD около 0). См. [RESEARCH.md](../../RESEARCH.md).
