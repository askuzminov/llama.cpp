# Пул серверов: настройка

Пул - часть роутера (`serve.bat`). Машины с одной моделью делят запросы агентов между собой: отдельного процесса,
порта и файла настройки нет. Каждая машина пула и принимает запросы, и считает их:

- запрос уходит на машину (узел) со свободным слотом; если свободных нет, ждёт в очереди (первым идёт тот, кто пришёл
  раньше);
- новый разговор уходит на узел с большей долей свободных слотов с учётом его скорости генерации; если доли равны -
  на узел, где уже посчитан общий системный промпт агента;
- продолжение разговора уходит со своего узла на свободный, если на своём заметно больше запросов в работе (примерно на
  два потока с учётом скорости узлов), а перенос состояния или пересчёт займёт не больше `pool-rebalance-s` (15 с);
  один разговор переезжает так не чаще раза в 5 минут;
- на узел с общим KV (`kv-unified = true`) запрос идёт, только если его разговор помещается в контекст рядом с тем, что
  держат работающие слоты (с резервом под их ответы), как считает сам узел. Иначе он ждал бы места внутри узла, даже
  когда другой узел уже свободен; теперь ждёт в очереди пула и уходит на первый узел, где место есть. На карточке
  узла это `KV held N / M`;
- запрос с длинным промптом (`pool-move-tokens` токенов и больше) идёт на узел, где сейчас ничего не идёт: промпт
  ставит на паузу генерацию своего узла, пока не прочитан. Если такого узла нет, он ждёт, пока узел освободится, но не
  дольше, чем стоила бы пауза, и не больше `pool-quiet-wait-s` (60 с);
- запрос за коротким ответом (`max_tokens` до `pool-short-tokens`, 512) идёт в очереди раньше запросов за длинным:
  так агент не стоит, пока ждёт проверку разрешения Auto Mode Qwen Code (она просит 256 токенов); тихого узла такой
  запрос не ждёт. Сами узлы ставят чекпоинт на конце длинного системного промпта (`LLAMA_CKPT_SYSTEM_BREAK`, от 1024
  токенов, 0 - выключить), поэтому общий системный промпт этих проверок (~2.9K токенов из ~12K) берётся из кэша;
- разговор остаётся на узле, где лежит его кэш промпта, и там считаются только новые сообщения;
- если узел разговора занят или выведен, разговор уходит на другой узел вместе со своим состоянием, когда это быстрее
  пересчёта (перенос, см. ниже); состояние новый узел читает со старого сам;
- узлы находят друг друга сами, по каждой сети машины (кабель и WiFi), и сами меряют скорость каналов;
- на `http://<машина>:12345/pool` открывается дашборд: узлы, слоты, скорость, память, очередь, разговоры, решения.

## Схема

Пример: 395a, 395b и 3090. У 395a и 395b прямой кабель 10 Гбит, все три машины в WiFi.

```text
агенты (Qwen Code) --> любая машина :12345 --+--> себе                395a, 395b или 3090
                                             +--> кабель или WiFi      другие две машины
```

Агенты могут ходить на любую машину пула. Удобнее всем ходить на одну: тогда у пула одна очередь, и разговор, который
агент продолжает, точно попадёт к тому, кто его помнит.

## Шаг 1. models.ini (на каждой машине)

В секции модели строка `pool = on`:

```ini
; models.ini на 395a и 395b
[qwen3.8]
model = C:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf
pool = on

; models.ini на 3090: своё имя секции, общее имя - alias
[qwen3.8-3090]
model = E:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf
alias = qwen3.8
pool = on
```

- Модели машин объединяются по имени: имени секции или `alias`, которое есть у обеих. Здесь это `qwen3.8`. Пул шлёт
  каждой машине это общее имя.
- Имя и путь файла GGUF значения не имеют. Модель пул сверяет по параметрам из `/pool/node`: число параметров, размер,
  тип квантования, словарь, обучающий контекст. Узел с другой моделью (например, другим квантом) получает статус
  `mismatch` и запросов не получает.
- Нужна сборка форка на всех машинах. `serve.bat` запускается как обычно: роутер на порту 12345, `--host 0.0.0.0` уже
  стоит в `SRVARGS`.
- Модель загружается по спросу, `load-on-startup` не нужен. Первый запрос к модели пула просит загрузить её все
  машины пула, где она ещё не загружена и где хватает места (`--models-max` не занят другими моделями). Пока они
  грузятся, запросы идут на машины, где модель уже есть, а если её нет нигде, ждут в очереди пула. Новые разговоры
  потом расходятся по машинам с большим числом свободных слотов. Если модели нет нигде и места тоже нет, загрузку
  получает одна машина (сначала своя), и её роутер выгружает другую модель, как без пула.
- Моделей с `pool = on` может быть несколько: у каждой свой пул со своей очередью, машины находятся для всех сразу.
  Дашборд одного из них - `http://<машина>:12345/pool?model=<имя>`, ссылки на остальные - в шапке.

## Шаг 2. Агенты (Qwen Code)

```text
OPENAI_BASE_URL=http://<машина пула>:12345/v1
OPENAI_API_KEY=любой (или ключ из --api-key, если он задан)
OPENAI_MODEL=qwen3.8        # имя модели или любой её alias
```

Через пул идут запросы к модели с `pool = on` под любым её именем. Запросы к другим моделям этого роутера идут, как
без пула. Пул узнаёт разговор по истории сообщений. Если клиент шлёт `X-Conversation-Id` или `X-Session-Id`, пул
берёт разговор из заголовка.

## Шаг 3. Проверка

`http://<машина>:12345/pool`: до первого запроса узлы без загруженной модели стоят `unloaded`, после него
`loading`, затем `up` (в решениях - `load`). Когда модель загрузилась: у каждого узла в строке под именем подпись
`cache xxxxxxxx`, внизу карточки
`moves state yes`, в разделе Links у каналов `from N / to M MB/s measured`. Карточка своей машины помечена
`this router`. Каждая машина показывает пул со своей стороны: свою очередь и свои разговоры. Запросы, которые
пришли на узел через другую машину, видны на его карточке как `other routers`.

С `--api-key` страница открывается так: `http://<машина>:12345/pool?key=<ключ>`.

## Как машины находят друг друга

- Роутер с `pool = on` рассылает по UDP на порт 12345 широковещательный пакет в каждую сеть машины: первые 30 с
  раз в 2 с, потом раз в 15 с. Роутер с той же моделью отвечает, и машины добавляют друг друга. В решениях это
  `found` (`link+` - ещё один адрес уже известного узла).
- Машина, которую видно и по кабелю, и по WiFi, получает два канала. Скорость каждого пул меряет сам: блок переноса
  (16 МиБ, `/pool/probe`) с узла и на узел. Работает более быстрый, другой - запасной. Если канал перестал
  отвечать, пул переходит на другой; раз в 10 с пробует более быстрый и возвращается на него. Каждая смена канала
  видна в решениях как `link`.
- Прямому кабелю нужны статические адреса на обоих концах, без шлюза. Например, на 395a адаптер 10G:
  `10.10.0.1/255.255.255.0`, на 395b: `10.10.0.2/255.255.255.0`.
- Брандмауэр Windows: при первом запуске разрешить входящие подключения к `llama-server.exe`. Правило для программы
  открывает и TCP, и UDP. Сеть кабеля Windows считает неопознанной и относит к общедоступным: разрешение нужно и для
  общедоступных сетей, или сети кабеля назначают профиль частной (PowerShell от администратора:
  `Set-NetConnectionProfile -InterfaceAlias "<имя адаптера>" -NetworkCategory Private`).
- `--api-key`: один и тот же на всех машинах (в `SRVARGS` в `serve.bat`). Тогда машина принимает другую, только
  когда та ответила на её пакет хешем от ключа и случайного числа из пакета; сам ключ уходит только на такой адрес.
  Машина с другим ключом в пул не попадает. Без ключа любой, кто достучится до порта, может слать запросы и забрать
  состояние разговора (в нём весь текст разговора); роутер проверяет ключ на всех адресах, кроме `/health`, файлов
  интерфейса и страницы `/pool`, а его дочерние процессы слушают только 127.0.0.1.
- Сеть без широковещания (машины в разных подсетях, VPN): адреса других машин задаёт `pool-peers` рядом с
  `pool = on`: `pool-peers = 192.168.1.31:12345, 192.168.1.30:12345`.

## Перенос разговора

Перенос срабатывает, когда следующий запрос разговора уходит не на тот узел, где лежит его кэш: узел занят и ждать
дольше, чем переносить, или узел выведен через Drain.

Сколько разговора уже есть на другом узле, пул считает так: то, что узел посчитал для самого этого разговора, -
целиком, а общий с другими разговорами префикс (системный промпт и инструменты агента) - с долей, которую узел из
такого префикса на деле берёт из кэша. Долю пул меряет сам по `cache_n` в таймингах ответов, когда узел держал общий
префикс от других разговоров (от `pool-move-tokens` токенов). Трансформер берёт префикс весь, гибридная модель
(qwen4exp) и SWA - только до контрольной точки внутри него. До первого замера доля 0.

### Когда перенос возможен

- Оба узла - сборка форка с кэшем промптов (`moves state yes` на карточке).
- Подписи кэша одинаковые (`cache xxxxxxxx` на карточках). Подпись зависит от формата состояния: модели (размеров её
  файлов), типов KV (`cache-type-k/v`), `swa-full`, RoPE, LoRA, mmproj, черновой модели или головы MTP и её окна KV.
  Путь к модели, даты файлов, `-c`, `-np` и `--kv-unified` на подпись не влияют: состояние одного разговора несёт
  ячейки одного потока KV и ложится в поток своего слота на новом узле при любом числе потоков (с 03.11). Окно KV
  головы MTP у qwen4exp одинаково при любом `-np` (`LLAMA_MTP_WINDOW_KV`, по умолчанию 1 с 01.11), если его не
  задали на одном узле иначе.
- У разговора на старом узле не меньше `pool-move-tokens` (4096) токенов истории, которые новый узел реально
  возьмёт.

### Как идёт перенос

0. Если по прошлым переносам (байт на токен, скорость канала) уже ясно, что пересчёт разницы короче переноса,
   экспорта не будет: в решениях `move ... no state moved: ... (estimate)`. Экспорт копирует всё состояние на старом
   узле (гигабайты), а 03.11 у пользователя 10 из 13 экспортов отбрасывались по этой причине.
1. Машина, которая приняла запрос, отправляет старому узлу запрос разговора (`POST /pool/export`). Узел берёт
   состояние с самым длинным общим префиксом из слота или кэша промптов. Состояние, которое уже лежит на диске,
   отдаётся из своего файла. Состояние только в RAM копируется в памяти, пока работающие слоты ждут (memcpy, доли
   секунды на гигабайт). На диск ничего не пишется.
2. Узел отвечает, сколько токенов запроса новый узел возьмёт из состояния (`n_reuse`), и размер. Пул отказывается от
   переноса, если это меньше `pool-move-tokens`, если состояние больше кэша промптов в RAM нового узла (`cache-ram`) или
   если перенос по оценке не быстрее пересчёта. Оценка переноса: 0.2 с, плюс размер, делённый на скорость канала
   нового узла к старому (как её замерил новый узел), плюс размер / 2 ГБ/с на копии на узлах. Оценка пересчёта:
   то, что состояние даёт сверх уже лежащего на новом узле (`n_reuse` минус его кэш), делённое на скорость префилла
   нового узла. Отказ виден в решениях как `move ... no state moved: ...`.
3. Новый узел получает команду `POST /pool/pull` и сам читает состояние со старого блоками по 16 МБ, по своему
   каналу к нему; чтение по сети и разбор блоков идут одновременно. Машина, которая приняла запрос, через себя
   данные не гонит.
4. Новый узел собирает блоки сразу в RAM, в буферы будущего состояния, и кладёт его в кэш промптов. Туда же уходит
   запрос: узел восстанавливает состояние в слот и считает только новые сообщения. Пока запрос не пришёл, принятое
   состояние в простое на диск не пишется. В решениях это
   `migrate ~N tok from X (RAM | its file): M MB in S s (read V MB/s), K of L checkpoints`.
5. Если что-то сорвалось (узел упал, канал оборвался, клиент ушёл), перенос бросается. Память на обоих узлах
   освобождается, и запрос считается на новом узле с нуля, как без переноса.

### Что переносится

Состояние разговора (KV слоёв внимания, рекуррентное состояние, состояние черновика MTP) и та одна контрольная точка,
которую возьмёт этот запрос. Её узел выбирает по тому же правилу, что и восстановление слота: самая новая точка внутри
общего с запросом префикса. У SWA-моделей с ней едет база её цепочки дельт.

- Если запрос продолжает состояние с его конца, точек не нужно.
- Если шаблон по-другому отрисовал последний ответ (например, убрал из него рассуждение), это точка в конце прошлого
  промпта.
- Если правили последнее сообщение, это точка в начале этого сообщения.

### Размер состояния

После первого переноса пул пишет в шапке дашборда `state ~N KiB/tok`. Оценка для qwen4exp по буферам из лога 12.10
(KV 6144 МиБ и KV индексатора 768 МиБ на 262144 ячейки): около 27 КиБ на токен, плюс рекуррентное состояние около
0.1 ГБ. Это расчёт, а не замер переноса.

| | 100K токенов (около 2.8 ГБ) |
| --- | --- |
| WiFi 650 Мбит/с (около 75 МБ/с) | около 37 с |
| кабель 10 Гбит | около 3 с |
| пересчёт при 700 т/с | 140 с |

Данные идут от экземпляра модели старого узла через его роутер, по сети в роутер нового узла и в его экземпляр.
Настоящую скорость показывает решение `migrate` (`read V MB/s`).

Состояние должно поместиться в кэш промптов нового узла: по умолчанию (`cache-ram = -1`) кэш берёт всю свободную RAM,
кроме запаса `cache-ram-reserve` (авто: 1/16 RAM, от 0.5 до 2 ГиБ).

Ожидание с переносом: разговор ждёт свой занятый узел не дольше, чем занял бы перенос. Пока не было ни одного
переноса, байты на токен неизвестны, и разговор переносится сразу, не дожидаясь.

Вывести узел, например перед перезапуском: кнопка Drain на дашборде или
`POST /pool/drain {"node": "395b", "drain": true}`. Машина, у которой это сделали, новых запросов на узел не шлёт
(во всех своих пулах), идущие дорабатывают, следующий запрос каждого его разговора переезжает на другой узел вместе
с состоянием. Resume (`"drain": false`) возвращает узел. Вывод действует на ту машину, где нажали, другие машины пула
шлют на узел как раньше.

## Что пул меряет сам

| Что | Как | До замера |
| --- | --- | --- |
| слоты узла | `/props` узла (`-np`) | - |
| скорость канала | блок 16 МиБ в каждую сторону, когда канал впервые ответил; дальше переносы | 500 Мбит/с |
| скорость префилла | тайминги ответов на промпты от `pool-move-tokens` токенов | 700 т/с |
| скорость генерации | тайминги ответов от 16 токенов: по ней делятся новые разговоры (вес узла - его скорость против самого быстрого) | вес 1 |
| доля общего префикса | `cache_n` ответов, когда узел держал общий префикс от других разговоров | 0 |

## Параметры пула в models.ini

Все необязательные, в обычной работе не нужны. Пишутся рядом с `pool = on` в секции модели (или в `[*]`):

```ini
[qwen3.8]
model = C:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf
pool = on
pool-name = 395a
pool-move-tokens = 2048
```

Неверное значение (не число) останавливает запуск роутера, в логе - имя ключа.

| Ключ | По умолчанию | Что делает |
| --- | --- | --- |
| `pool-name` | имя машины | как узел называется в пуле; с портом это id узла, у машин он должен различаться |
| `pool-peers` | | `host:port, ...` машин пула, которые добавляются без поиска |
| `pool-port` | 12345 | UDP-порт поиска, один на все машины |
| `pool-discover` | 1 | 0 - без широковещания, только `pool-peers` |
| `pool-move-tokens` | 4096 | столько токенов своей истории на занятом узле - разговор ждёт его (см. `pool-wait-max`); короче - сразу на свободный. Это же порог для переноса состояния и для замера скорости префилла |
| `pool-wait-max` | 300 | дольше этого (с) разговор свой узел не ждёт |
| `pool-migrate` | 1 | 0 - не переносить состояние никогда |
| `pool-link-mbps` | 500 | скорость канала до замера (Мбит/с) |
| `pool-prefill-tps` | 700 | скорость префилла до замера (т/с) |
| `pool-poll-ms` | 1000 | как часто опрашивается каждый узел (мс) |
| `pool-probe-s` | 10 | как часто узел на более медленном канале пробует более быстрый (с) |
| `pool-same-model` | 1 | 0 - узел с другой моделью тоже получает запросы (перенос между разными моделями всё равно невозможен) |
| `pool-rebalance-s` | 15 | разговор уходит с перегруженного узла на свободный, если переезд стоит не больше стольких секунд; 0 - никогда |
| `pool-quiet-wait-s` | 60 | дольше этого (с) длинный промпт не ждёт узла, где ничего не идёт; 0 - не ждать |
| `pool-short-tokens` | 512 | запрос с `max_tokens` не больше этого идёт в очереди раньше длинных (если длинный не ждёт уже `pool-wait-max`); 0 - очередь по порядку |

## На узлах (`models.ini` или аргументы `serve.bat`)

| Параметр | Что делает |
| --- | --- |
| `pool` | `on` в секции модели включает пул для неё; `pool-*` - параметры пула (выше) |
| `cache-ram` | размер кэша промптов в RAM (МиБ); `-1` (по умолчанию) - без лимита: вся свободная RAM, кроме запаса `cache-ram-reserve`; больше заданного числа состояние на узел не переносится; `0` выключает кэш, а с ним и перенос |
| `cache-ram-reserve` | сколько RAM кэш оставляет свободной (МиБ); `-1` - авто, 1/16 RAM от 0.5 до 2 ГиБ; длинное вытесненное состояние уходит на диск |
| `cache-spill-dir` | кэш промптов на диске; для переноса не нужен. Если состояние уже лежит в нём, перенос читает его файл через жёсткую ссылку `pool-export-*.bin`, которую убирает в конце |
| `cache-min-tokens` | минимум токенов для записи на диск и шаг перезаписи; в кэше RAM короткие разговоры остаются, переносятся тоже |
| `cache-ram-min-tokens` | минимум токенов для кэша в RAM, по умолчанию 0 (все); разговор короче при занятом слоте считается заново |
| `--api-key` | один на все машины пула: закрывает запросы и перенос от чужих |
| `--host 0.0.0.0` | слушать сеть, а не только эту машину (в `serve.bat` уже стоит) |

## Дашборд

Плитки показывают узлы, занятые слоты, очередь, общую скорость генерации и промпта, разговоры. Карточка узла: адрес
(с пометкой `fallback`, когда работает не самый быстрый канал), модель и квант, контекст, слоты, вес, подпись кэша,
каналы, память устройств, запросы в работе (`moving` - идёт перенос). Кнопка Drain/Resume выводит и возвращает узел.

Скорости на карточке:

| Поле | Что это |
| --- | --- |
| `gen now` | сколько токенов в секунду генерируют все слоты узла сейчас (между двумя опросами); 0, когда никто не генерирует |
| `prompt now` | то же для промптов: сколько токенов промпта в секунду узел считает сейчас |
| `prefill` | средняя скорость чтения промпта одного запроса (из timings ответов с промптом от `pool-move-tokens`); по ней пул считает цену пересчёта разговора на этом узле; `(default)` - замера ещё не было, взят `pool-prefill-tps` |
| `decode` | средняя скорость генерации одного запроса (из timings ответов от 16 токенов, вместе с соседями по узлу); по ней пул делит новые разговоры между узлами (вес) |
| `shared prefix` | какую часть общего с другими разговорами начала (системный промпт и инструменты агента), лежащего на узле, узел действительно взял из кэша, среднее по таким запросам. Гибридная модель (qwen4exp: gated delta net) берёт его только до чекпоинта внутри этого начала: нет чекпоинта - всё считается заново |
| `KV held` | только узел с общим KV: сколько ячеек держат слоты с резервом под ответы, из скольких |

Ниже на карточке:

- `GPU`: температура, нагрузка по мощности (процент лимита) и вентилятор, как их отдаёт система. Windows - те же данные
  драйвера, что показывает Диспетчер задач (только то, что драйвер сообщает; встроенная GPU может не сообщать
  температуру), Linux - hwmon карты. Нет данных - строки нет.
- `Work since the model loaded`: сколько токенов промпта узел посчитал и с какой средней скоростью, сколько
  сгенерировал (средняя скорость одного слота), сколько токенов взял из кэша вместо пересчёта; с загрузки модели.

События в таблице решений:

| Событие | Что значит |
| --- | --- |
| `found`, `link+` | найден узел; найден ещё один адрес узла |
| `load` | запросы к модели попросили роутер узла загрузить её (или он ответил, почему не может) |
| `conflict` | у роутера другой машины то же имя машины и порт: они не различают друг друга, одному нужен `pool-name` |
| `new` | новый разговор, ушёл на узел со свободным слотом |
| `keep` | разговор остался на своём узле |
| `move` | разговор ушёл на другой узел без состояния (там контекст считается заново), с причиной |
| `migrate` | разговор ушёл на другой узел с состоянием |
| `cold` | ни один узел не держит этот разговор |
| `link` | узел переключился на другой канал |
| `up`, `down`, `loading`, `unloaded` | состояние узла |
| `mismatch`, `match` | узел с другой моделью исключён / снова в строю |
| `drain`, `undrain` | узел выведен / возвращён |
| `done`, `error` | запрос закончился: HTTP-код, время, промпт и ответ из timings узла (токены, секунды, скорость ответа) и `the rest` - остальное время: перенос состояния перед запросом, очередь на узле (место в общем KV, слоты), сеть |
| `gone`, `fail` | клиент ушёл из очереди (или роутер останавливается); ни один узел не поднялся за 30 с |

JSON всего этого отдаёт `GET /pool/status`; `GET /pool/router` - то, что читают другие машины пула (имена модели,
каналы этой машины к остальным).

## Если что-то не так

- Узла нет на дашборде: брандмауэр (для сети кабеля - профиль общедоступной сети), другой `--api-key`, другое имя
  модели (ни имя секции, ни `alias` не совпадают), машины в разных подсетях (тогда `pool-peers`). Найденные
  узлы роутер пишет в лог: `pool: found <узел> at <адрес>`.
- Узел `down`: ошибка написана на карточке. При нескольких каналах в Links видно, какой из них не отвечает и почему.
- Узел `unloaded` с `the model ... failed to load, exit code N`: модель на той машине не загрузилась, причина - в логе
  её роутера. Пул просит загрузку снова через 5 минут, пока к модели идут запросы: на 395 загрузке изредка не хватает
  памяти устройства (`ErrorOutOfDeviceMemory` в логе), и следующая проходит.
- Узел `unloaded` без ошибки загрузки после запросов: у его роутера нет места (`--models-max` занят другими моделями),
  а модель уже работает на других машинах.
- `moves state no`: на узле выключен кэш промптов (`cache-ram 0`). Узел сам сообщает это в `GET /pool/node`
  (`"migrate": false`).
- Подписи кэша на узлах разные, переносов нет: другой GGUF, другие `cache-type-k/v`, `swa-full`, разный
  `LLAMA_MTP_WINDOW_KV` или `LLAMA_MTP_WINDOW`, разная голова MTP, разные LoRA или mmproj.
- `move ... no state moved: the move of N MB would take ~X s, computing the ~T tok it brings ~Y s`: перенос медленнее
  пересчёта тех T токенов, которые состояние дало бы сверх кэша нового узла (часто на новом узле уже лежит старая копия
  разговора). С `(estimate)` - по оценке, без экспорта. Поведение правильное.
- `move ... no state moved: the state reaches ~N tok (a checkpoint), the node holds ~M`: состояние старого узла годится
  только до чекпоинта, а новый узел и так держит больше.
- `done` с большим `the rest`: запрос долго ждал внутри узла. На узле с общим KV (`--kv-unified`) так бывает, когда
  разговоры слотов вместе не помещаются в контекст: новый ждёт места. Пул такие запросы туда не шлёт (`move ... (no KV
  room, N in work)`), но оценка токенов по символам грубая, а другие роутеры пула могут прислать запрос между опросами.
- Узел с общим KV получает меньше запросов, чем у него слотов: разговоры агентов вместе не помещаются в его контекст.
  Помогает `kv-unified = false` с `ctx-size` = число слотов x 262144 (у каждого слота свой контекст) или меньше слотов.
- `move ... no state moved: no state: ...`: старый узел уже вытеснил состояние из кэша (не хватило места или его
  перезапустили без кэша на диске), или запрос берёт из состояния меньше `pool-move-tokens` токенов.
- `move ... no state moved: pull: ... no node ...`: новый узел ещё не нашёл старый (несколько секунд после старта).
- `move ... no state moved: the state of N MB is larger than the prompt cache of X`: поднять `cache-ram` на узле X.
- `mismatch`: на узле другая модель, чем на остальных.
- Первые запросы после перезапуска роутера: он ещё не знает разговоров и раскладывает их как новые.
