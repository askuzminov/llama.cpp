# Пул серверов: настройка

Пул (`llama-server --pool pool.ini`, `pool.bat`) даёт агентам один адрес перед серверами нескольких машин с одной
моделью. Сам он модель не загружает и только раздаёт запросы по узлам:

- запрос уходит на узел со свободным слотом; если свободных нет, ждёт в очереди пула (первым идёт тот, кто пришёл раньше);
- разговор остаётся на узле, где лежит его кэш промпта, и там считаются только новые сообщения;
- если узел разговора занят или выведен, разговор уходит на другой узел вместе со своим состоянием, когда это быстрее
  пересчёта (перенос, см. ниже);
- до узла можно задать несколько адресов по приоритету: сначала прямой кабель, потом WiFi;
- на `http://<машина пула>:12346/pool` открывается дашборд: узлы, слоты, скорость, память, очередь, разговоры, решения.

## Схема

Пример: 395a, 395b и 3090. Пул запущен на 395a, у 395a и 395b прямой кабель 10 Гбит, все три машины в WiFi.

```text
агенты (Qwen Code) --> 395a:12346 (пул) --+--> 127.0.0.1:12345     395a, serve.bat
                                          +--> 10.10.0.2:12345      395b, кабель (запасной адрес - WiFi)
                                          +--> 192.168.1.30:12345   3090, WiFi
```

При переносе данные идут через пул: узел -> пул -> узел. Поэтому пул лучше держать на машине с кабелем: тогда один из
двух участков идёт по кабелю или внутри машины.

## Шаг 1. Узлы (на каждой машине)

1. На всех узлах должна быть сборка форка. Модель везде одна и та же: тот же GGUF, имя файла и путь к нему могут
   отличаться.
2. `serve.bat` запускается как обычно (роутер на порту 12345, `--host 0.0.0.0` уже стоит в `SRVARGS`). Для
   переноса разговоров ничего добавлять не нужно: его умеет любой узел форка с кэшем промптов (он включён по
   умолчанию), `cache-spill-dir` для него тоже не нужен.
3. Брандмауэр Windows: при первом запуске разрешить входящие подключения к `llama-server.exe` (порт 12345 на узлах,
   12346 на машине пула).
4. Если в сети есть чужие устройства, задать `--api-key <ключ>` на узлах (в `SRVARGS` в `serve.bat`) и тот же ключ в
   `api_key` в `pool.ini`. Без ключа любой, кто достучится до порта узла, может не только слать запросы, но и забрать
   состояние разговора (в нём токены промпта, то есть весь текст разговора) или подложить узлу своё. Роутер проверяет
   ключ на всех адресах, кроме `/health` и файлов интерфейса, а его дочерние процессы слушают только 127.0.0.1.
   Агентам ключ не нужен: они ходят в пул.

## Шаг 2. Пул (на одной машине)

1. Скопировать `pool.example.ini` в `pool.ini` рядом с `pool.bat` и вписать адреса и имена (параметры описаны ниже).
2. Запустить `pool.bat`. Он слушает порт 12346 (`POOLARGS`). Остановка пула узлы не трогает.
3. Открыть `http://<машина пула>:12346/pool`: все узлы должны быть `up`, у каждого в строке под именем видна подпись
   `cache xxxxxxxx`, а внизу карточки `moves state yes`.

Окно KV головы MTP у qwen4exp с 01.11 включено при любом числе слотов (`LLAMA_MTP_WINDOW_KV`, по умолчанию 1), так
что состояния узлов с одним слотом (3090) и с четырьмя (395) одного формата. На 3090 это значит ещё и меньше памяти
под KV головы: 16384 + ubatch ячеек вместо всего контекста (по расчёту около 34 МиБ вместо 512). Ответы модели не
меняются: голова и раньше смотрела только на окно, черновики проверяет основная модель. Первый запуск новой сборки
на 3090 удалит его старые файлы кэша промптов на диске (другая подпись).

## Шаг 3. Агенты (Qwen Code)

Пул отвечает как обычный OpenAI-совместимый сервер:

```text
OPENAI_BASE_URL=http://<машина пула>:12346/v1
OPENAI_API_KEY=любой (или ключ из --api-key в POOLARGS, если он задан)
OPENAI_MODEL=qwen3.8        # имя из [pool] model
```

Агенты просто ходят на этот адрес, никакой привязки к узлам с их стороны не нужно. Пул узнаёт разговор по истории
сообщений. Если клиент шлёт `X-Conversation-Id` или `X-Session-Id`, пул берёт разговор из заголовка.

## Два адреса узла: кабель и WiFi

```ini
[node.395b]
url = http://10.10.0.2:12345 10000, http://192.168.1.31:12345 650
```

- Порядок адресов задаёт приоритет. Пул опрашивает узел по первому адресу, который отвечает. Если адрес перестал
  отвечать, пул переходит на следующий. Пока узел сидит на запасном адресе, раз в `probe_s` секунд пул пробует
  адреса перед ним и возвращается на первый ответивший.
- Скорость канала пул меряет сам: когда канал начинает обслуживать узел, пул читает с узла и пишет на него по одному
  блоку переноса (16 МиБ, `/pool/probe`), дальше замер уточняют переносы. На карточке узла в разделе Links:
  `from N / to M MB/s measured` (с узла и на узел). Число после адреса (Мбит/с), а без него `link_mbps`, нужны только
  до замера и если он не удался (узел старой сборки без `/pool/probe`).
- Свой узел пул видит по `127.0.0.1`: так данные не выходят в сеть.
- Прямому кабелю нужны статические адреса на обоих концах, без шлюза. Например, на 395a адаптер 10G:
  `10.10.0.1/255.255.255.0`, на 395b: `10.10.0.2/255.255.255.0`.
- Запрос, который шёл по отвалившемуся каналу, обрывается (агент его повторит), новые запросы идут по запасному.
- Каждая смена канала попадает в решения на дашборде как `link`.

## Одна модель под разными именами

Здесь три разных имени, и каждое настраивается отдельно:

1. Имя модели на узле: имя её секции в `models.ini` этой машины или её `alias`. Задаётся в секции узла:
   `model = <имя на этом узле>`, для каждого узла отдельно. Пул подставляет его в каждый запрос к этому узлу (в теле
   POST, в `?model=` у GET), так что пресеты могут называться по-разному. Роутер без имени модели или с чужим именем
   запрос не принимает, поэтому для узла с `serve.bat` строка обязательна.
2. Имя, которое видят агенты: `[pool] model = qwen3.8`. Задаётся один раз, может быть любым, узлам не передаётся.
   Пул сам отвечает на `/v1/models` этим именем, от какого бы узла ни пришёл ответ. Агент может прислать любое имя:
   роутер получит своё (п. 1), простой `llama-server` имя игнорирует.
3. Имя и путь файла GGUF значения не имеют. Модель пул сверяет по параметрам из `/pool/node`: число параметров,
   размер, тип квантования, словарь, обучающий контекст. Узел с другой моделью (например, другим квантом) получает
   статус `mismatch` и запросов не получает (`same_model = 1`; при равенстве голосов эталоном считается узел, который
   выше в `pool.ini`). `same_model = 0` снимает это ограничение, но перенос состояния между разными моделями всё равно
   невозможен.

Пример. На 395a и 395b модель в `models.ini` лежит в секции `[qwen3.8]`, на 3090 - в секции под своим именем и с
`alias`:

```ini
; models.ini на 395a и 395b
[qwen3.8]
model = C:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf

; models.ini на 3090
[qwen3.8-3090]
model = E:\models\Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf
alias = qwen3.8
```

Тогда в `pool.ini`:

```ini
[pool]
; имя для агентов (OPENAI_MODEL), узлам не передаётся
model = qwen3.8

[node.395a]
url = http://127.0.0.1:12345
model = qwen3.8

[node.395b]
url = http://10.10.0.2:12345, http://192.168.1.31:12345
model = qwen3.8

[node.3090]
url = http://192.168.1.30:12345
; имя секции на 3090; по alias подошло бы и qwen3.8, без строки alias - только qwen3.8-3090
model = qwen3.8-3090
```

Агенты просят у пула `qwen3.8`, а пул отправляет 395a и 395b имя `qwen3.8`, а 3090 - `qwen3.8-3090`.

## Перенос разговора

Перенос срабатывает, когда следующий запрос разговора уходит не на тот узел, где лежит его кэш: узел занят и ждать
дольше, чем переносить, или узел выведен через Drain.

Сколько разговора уже есть на другом узле, пул считает так: то, что узел посчитал для самого этого разговора, -
целиком, а общий с другими разговорами префикс (системный промпт и инструменты агента) - с долей, которую узел из
такого префикса на деле берёт из кэша. Долю пул меряет сам по `cache_n` в таймингах ответов, когда узел держал общий
префикс от других разговоров (от `move_tokens` токенов). Трансформер берёт префикс весь, гибридная модель (qwen4exp)
и SWA - только до контрольной точки внутри него. До первого замера доля 0.

### Когда перенос возможен

- Оба узла - сборка форка с кэшем промптов (`moves state yes` на карточке).
- Подписи кэша одинаковые (`cache xxxxxxxx` на карточках). Подпись зависит от формата состояния: модели (размеров её
  файлов), типов KV (`cache-type-k/v`), `swa-full`, RoPE, LoRA, mmproj, черновой модели или головы MTP и её окна KV, а
  также от числа потоков KV. Путь к модели, даты файлов и `-c` на подпись не влияют.
- `-np` на подпись не влияет, кроме одного случая: при `-np` больше 1 без `--kv-unified` у KV столько потоков,
  сколько слотов, а состояние записывает их число. Такой узел совместим только с узлом с тем же `-np`. При
  `--kv-unified` (или без `-np`: тогда 4 слота и общий KV) поток один, как при `-np 1`. Узлам 395 общий KV нужен и так:
  без него каждому слоту достаётся только `-c / -np`. Окно KV головы MTP одинаково при любом `-np` (см. выше), если
  `LLAMA_MTP_WINDOW_KV` не задан на одном узле иначе, чем на другом.
- У разговора на старом узле не меньше `move_tokens` токенов истории, которые новый узел реально возьмёт.

### Как идёт перенос

1. Пул отправляет старому узлу запрос разговора (`POST /pool/export`). Узел берёт состояние с самым длинным общим
   префиксом из слота или кэша промптов. Состояние, которое уже лежит на диске, отдаётся из своего файла. Состояние
   только в RAM копируется в памяти, пока работающие слоты ждут (memcpy, доли секунды на гигабайт). На диск ничего не
   пишется.
2. Узел отвечает, сколько токенов запроса новый узел возьмёт из состояния (`n_reuse`), и размер. Пул отказывается от
   переноса, если это меньше `move_tokens`, если состояние больше кэша промптов в RAM нового узла (`cache-ram`) или
   если перенос по оценке не быстрее пересчёта. Оценка переноса: 0.2 с, плюс размер, делённый на скорость более
   медленного из двух каналов, плюс размер / 2 ГБ/с на копии на узлах. Оценка пересчёта: `n_reuse`, делённое на
   скорость префилла нового узла. Отказ виден в решениях как `move ... no state moved: ...`.
3. Пул читает состояние блоками по 16 МБ и пишет их новому узлу; чтение и запись идут одновременно.
4. Новый узел собирает блоки сразу в RAM, в буферы будущего состояния, и кладёт его в кэш промптов
   (`POST /pool/import/done`). Туда же уходит запрос: узел восстанавливает состояние в слот и считает только новые
   сообщения. Пока запрос не пришёл, принятое состояние в простое на диск не пишется. В решениях это
   `migrate ~N tok from X (RAM | its file): M MB in S s (V MB/s), K of L checkpoints`.
5. Если что-то сорвалось (узел упал, канал оборвался, клиент ушёл), пул бросает перенос. Память на обоих узлах
   освобождается, и запрос считается на новом узле с нуля, как без переноса.

### Что переносится

Состояние разговора (KV слоёв внимания, рекуррентное состояние, состояние черновика MTP) и та одна контрольная точка,
которую возьмёт этот запрос. Её узел выбирает по тому же правилу, что и восстановление слота: самая новая точка внутри
общего с запросом префикса. У SWA-моделей с ней едет база её цепочки дельт.

- Если запрос продолжает состояние с его конца, точек не нужно.
- Если шаблон по-другому отрисовал последний ответ (например, убрал из него рассуждение), это точка в конце прошлого
  промпта.
- Если правили последнее сообщение, это точка в начале этого сообщения.

Проверка на Mac (LFM2, гибрид): после правки последнего ответа экспорт обещал 515 токенов из 542, новый узел взял из
кэша 515 и посчитал 21. Раньше без точек было 550 токенов пересчёта.

### Размер состояния

После первого переноса пул пишет в шапке дашборда `state ~N KiB/tok`. Оценка для qwen4exp по буферам из лога 12.10
(KV 6144 МиБ и KV индексатора 768 МиБ на 262144 ячейки): около 27 КиБ на токен, плюс рекуррентное состояние около
0.1 ГБ. Это расчёт, а не замер переноса.

| | 100K токенов (около 2.8 ГБ) |
| --- | --- |
| WiFi 650 Мбит/с (около 75 МБ/с) | около 37 с |
| кабель 10 Гбит | около 3 с |
| пересчёт при 700 т/с | 140 с |

Через роутер (`serve.bat`) данные идут ещё через один процесс, и для кабеля это может быть узким местом: на Mac блок
16 МиБ шёл через роутер 37-60 мс, напрямую к экземпляру 7 мс. Настоящую скорость пул покажет в разделе Links.

Состояние должно поместиться в кэш промптов нового узла: по умолчанию это четверть RAM машины (`cache-ram`).

Ожидание с переносом: разговор ждёт свой занятый узел не дольше, чем занял бы перенос. Пока не было ни одного
переноса, байты на токен неизвестны, и разговор переносится сразу, не дожидаясь.

Вывести узел, например перед перезапуском: кнопка Drain на дашборде или
`POST /pool/drain {"node": "395b", "drain": true}`. Новые запросы на узел не идут, идущие дорабатывают, следующий
запрос каждого его разговора переезжает на другой узел вместе с состоянием. Resume (`"drain": false`) возвращает узел.

## Параметры `pool.ini`

### `[pool]`

| Параметр | По умолчанию | Что делает |
| --- | --- | --- |
| `name` | | подпись на дашборде |
| `model` | | имя модели для агентов в `/v1/models`, любое, узлам не передаётся; пусто - как называет узел |
| `move_tokens` | 2048 | столько токенов своей истории на занятом узле - разговор ждёт его (см. `wait_max`); короче - сразу на свободный. Это же порог для переноса состояния (короче - пересчёт на новом узле) и для замера скорости префилла (промпты от стольких токенов) |
| `wait_max` | 300 | дольше этого (с) разговор свой узел не ждёт. Ожидание короче этого, если пересчёт на другом узле или перенос быстрее |
| `prefill_tps` | 700 | стартовая скорость пересчёта промпта (т/с) для оценок. Пул меряет скорость каждого узла сам по таймингам в конце ответов (промпты от `move_tokens` токенов) и дальше берёт замер; у узла может быть своё стартовое значение |
| `chars_per_token` | 3.5 | символов на токен, для оценки длины промпта по тексту |
| `affinity_ttl` | 21600 | сколько секунд пул помнит, какой узел держит какой префикс |
| `migrate` | 1 | переносить состояние разговора между узлами, когда оба узла могут и это быстрее пересчёта; 0 - никогда (выключатель, например для сравнения) |
| `link_mbps` | 500 | скорость канала (Мбит/с) без числа после адреса, пока пул её не измерил (замер, когда канал начинает работать) |
| `probe_s` | 10 | как часто узел на запасном адресе пробует адреса перед ним (с) |
| `same_model` | 1 | узел с другой моделью, чем у большинства, запросов не получает |
| `poll_ms` | 1000 | как часто опрашивается каждый узел (мс) |
| `api_key` | | ключ для узлов, у которых нет своего `api_key` |

### `[node.<имя>]`

| Параметр | Что делает |
| --- | --- |
| `url` | `http://host:port [Мбит/с], http://host:port [Мбит/с], ...` по приоритету |
| `model` | имя секции модели в `models.ini` этого узла или её `alias`, у узлов может различаться (узел - роутер `serve.bat`); для простого `llama-server` не нужен |
| `slots` | число параллельных запросов узла; по умолчанию берётся с узла (`-np`) |
| `weight` | доля новых разговоров (по скорости узла), по умолчанию 1 |
| `prefill_tps` | своя стартовая скорость пересчёта промпта, т/с, пока нет замера |
| `api_key` | ключ узла, если на нём `--api-key` |

### На узлах (`models.ini` или аргументы `serve.bat`)

| Параметр | Что делает |
| --- | --- |
| `cache-ram` | размер кэша промптов в RAM (МиБ), по умолчанию четверть RAM; больше этого состояние на узел не переносится; `0` выключает кэш, а с ним и перенос |
| `cache-spill-dir` | кэш промптов на диске; для переноса не нужен. Если состояние уже лежит в нём, перенос читает его файл через жёсткую ссылку `pool-export-*.bin`, которую убирает в конце |
| `cache-min-tokens` | минимум токенов для записи на диск и шаг перезаписи; перенос его не учитывает: разговор короче всё равно переносится |
| `--api-key` | ключ узла (тогда `api_key` в `pool.ini`): закрывает запросы и перенос от чужих |
| `--host 0.0.0.0` | слушать сеть, а не только эту машину (в `serve.bat` уже стоит) |

## Дашборд

Плитки показывают узлы, занятые слоты, очередь, общую скорость генерации и промпта, разговоры. Карточка узла: адрес
(с пометкой `fallback` на запасном), модель и квант, контекст, слоты, подпись кэша, каналы, память устройств,
запросы в работе (`moving` - идёт перенос), скорость префилла, по которой пул решает (`prefill N t/s`; с `(ini)` -
ещё значение из `pool.ini`, замера пока не было), доля общего префикса (`shared prefix N%`, `-` - замера пока не
было). Кнопка Drain/Resume выводит и возвращает узел.

События в таблице решений:

| Событие | Что значит |
| --- | --- |
| `new` | новый разговор, ушёл на узел со свободным слотом |
| `keep` | разговор остался на своём узле |
| `move` | разговор ушёл на другой узел без состояния (там контекст считается заново), с причиной |
| `migrate` | разговор ушёл на другой узел с состоянием |
| `cold` | ни один узел не держит этот разговор |
| `link` | узел переключился на другой адрес |
| `up`, `down`, `loading`, `unloaded` | состояние узла |
| `mismatch`, `match` | узел с другой моделью исключён / снова в строю |
| `drain`, `undrain` | узел выведен / возвращён |
| `done`, `error` | запрос закончился (HTTP-код, время) |
| `gone`, `fail` | клиент ушёл из очереди; ни один узел не поднялся за 30 с |

JSON всего этого отдаёт `GET /pool/status`.

## Если что-то не так

- Узел `down`: брандмауэр, нет `--host 0.0.0.0`, другой порт; ошибка написана на карточке. При нескольких адресах в
  Links видно, какой из них не отвечает и почему.
- `moves state no`: на узле выключен кэш промптов (`cache-ram 0`) или это не сборка форка. Узел сам сообщает это в
  `GET /pool/node` (`"migrate": false`).
- Подписи кэша на узлах разные, переносов нет: другой GGUF, другие `cache-type-k/v`, `swa-full`, `-np` больше 1 без
  `--kv-unified`, разный `LLAMA_MTP_WINDOW_KV` или `LLAMA_MTP_WINDOW`, разная голова MTP, разные LoRA или mmproj.
- `move ... no state moved: the move of N MB would take ~X s, computing ~Y s`: перенос медленнее пересчёта, например
  короткий разговор или медленный канал. Поведение правильное.
- `move ... no state moved: no state: ... 404`: старый узел уже вытеснил состояние из кэша (не хватило места или
  его перезапустили без кэша на диске), или запрос берёт из состояния меньше `move_tokens` токенов (`the request takes
  N tokens from the state`).
- `move ... no state moved: the state of N MB is larger than the prompt cache of X`: поднять `cache-ram` на узле X.
- `mismatch`: на узле другая модель, чем на остальных.
- Первые запросы после старта пула: пул ещё не знает разговоров и раскладывает их как новые.
