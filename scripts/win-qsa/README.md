# Проверки и замеры форка на 395 и 3090

Одни и те же скрипты на обеих машинах:

- **395** (Strix Halo, Vulkan, драйвер AMD): вся модель на GPU.
- **3090** (CUDA + i9): эксперты первых слоёв на CPU, горячие эксперты в кэше VRAM (`--moe-cache`).

Машина определяется по бэкенду сборки. Списки плеч и размеры по умолчанию у каждой свои,
они в конце `_config.bat`. Вся логика в `_run.py`, файлы `.bat` только вызывают его.

## Скрипты

| Файл | Модель | Что делает |
| --- | --- | --- |
| `00-build.bat` | нет | сборка в `build-win`; после удачной сборки кладёт рядом с бинарниками id исходников. `00-build.bat stable` собирает тег `stable` в отдельной worktree (`build-stable-src` -> `build-stable`) для плеч `@stable` |
| `01-check.bat` | нет | test-backend-ops: операции, которые менял форк, на GPU против CPU (`CHECKOPS` x `CHECKARMS`) |
| `02-bench.bat` | да | llama-bench: PP и TG на глубинах `BENCHDEPTHS`, по прогону на плечо и глубину |
| `03-quality.bat` | да | llama-perplexity: отношение PPL и KLD каждого плеча против опорного `QREF` |
| `04-decode.bat` | да | llama-server: генерация с MTP, кэшем экспертов, overlap CPU и GPU; длинный промпт через `DECPREFIX` |
| `05-profile.bat` | да | куда уходит время одного ubatch промпта или одного шага генерации: по операциям на Vulkan, по частям графа на CUDA |
| `run-all.bat` | да | 00, 01, 02, 03, 04, 05 по очереди (05 только на 395), `RUN_*` выключают шаги |
| `serve.bat` | да | повседневный запуск llama-server (router, `models.ini`), не замер |
| `get-wikitext.bat` | нет | текст для 03 и для `DECPREFIX` |

## Настройка машины

1. Скопировать `_local.example.bat` в `_local.bat`. Вписать `MODEL` (первый файл модели),
   `SPECDRAFT` (MTP-драфт для плеч с `@draft`). На 3090 ещё `EXTRA` со своим `-ncmoe`.
   `_config.bat` не править, иначе следующий `git pull` упрётся в него.
2. Нужен Python 3 (`py -3` или `python` в `PATH`).
3. `get-wikitext.bat` один раз, если будет 03.
4. `00-build.bat`, при желании `00-build.bat stable`.

Бэкенд выбирается сам: `nvcc` или `CUDA_PATH` -> CUDA, иначе `VULKAN_SDK` или `glslc` -> Vulkan.
`CMAKE_BACKEND` и `GENERATOR` в `_local.bat` нужны, только чтобы переопределить выбор.

CUDA под msbuild требует файлы интеграции. Установщик кладёт их только в ту Visual Studio,
которую видел при установке. Поэтому `00-build.bat` передаёт `-T cuda=%CUDA_PATH%` и берёт
файлы из тулкита. Если в тулките нет `extras\visual_studio_integration`, скрипт переходит на
Ninja и `cl` из `vcvarsall.bat`.

`00-build.bat` удаляет `build-win`, если кэш cmake остался от другого бэкенда, генератора или
тулкита. Он отказывается собирать, пока из `build-win` запущен llama-server.

## Что не запускается повторно

Каждый результат лежит в `cache\results` под ключом. Ключ складывается из:

- id исходников сборки;
- аргументов инструмента;
- переменных `GGML_*`, `LLAMA_*`, `CUDA_*` (из плеча и из консоли);
- файлов модели (пути, размеры, время изменения);
- входных данных (корпус, тексты промптов);
- имени машины.

Если ключ совпал, скрипт печатает сохранённый результат с пометкой `k` и модель не грузит.
Поэтому `run-all.bat` после правки кода меряет всё, а после правки скриптов или добавления
плеча меряет только новое.

- **id исходников** считает `00-build.bat` перед сборкой: `HEAD`, незакоммиченные изменения и
  новые файлы в `ggml`, `src`, `common`, `include`, `tools`, `vendor`, `cmake`, а также
  `tests/test-backend-ops.cpp`.
  - Каталоги чужих бэкендов не входят: правка в `ggml-cuda` не перезапускает замеры 395, и наоборот.
  - `scripts` не входит.
  - Повторная сборка того же кода даёт тот же id, хотя бинарники отличаются из-за коммита
    в build-info.
- Если сборка сделана не через `00-build.bat` или бинарник новее записи, ключом служит хеш бинарников.
- `set FORCE=1` в консоли запускает всё заново, `set FORCE=default-d32768` (регулярное выражение по имени замера) только совпавшие. Удаление `cache\` действует как `FORCE=1`.
  `FORCE=1` нужен после смены драйвера, настроек питания или фоновой нагрузки: ключ их не видит.
- Упавший замер не сохраняется и в следующий раз запустится снова.
  Тест test-backend-ops с FAIL сохраняется: на том же коде он упадёт так же.
- Опорные логиты 03 лежат в `cache\ref`, около 8 ГБ при `QCTX` 16384 и двух чанках.
  Хранятся последние `QREFKEEP` (2).

Перед каждым запуском с моделью скрипт ждёт, пока от конца прошлого пройдёт `SETTLE` секунд:
драйвер освобождает память процесса с задержкой. Если запуск всё же упал на памяти
(`ErrorOutOfDeviceMemory`, `failed to allocate`, `bad allocation`) или процесс умер без сообщения, скрипт пробует ещё дважды, ожидая `SETTLE` и `2 x SETTLE`.
Если запущен llama-server (например `serve.bat`), скрипт отказывается: сервер держит память GPU.

## Плечи

Плечо: `имя [VAR=value ...] [@stable | @<папка bin>] [@draft] [@d=глубины] [аргументы инструмента]`.
Плечи разделяются `;`.

- `VAR=value` (имя заглавными) идёт в окружение инструмента.
- `@stable` запускает сборку `00-build.bat stable`, `@<папка>` запускает бинарники из этой папки.
- `@draft` добавляет `-md SPECDRAFT` (только 04).
- `@d=122880` (через запятую) ограничивает плечо этими глубинами 02.
- Остальное дописывается к аргументам инструмента.

Пример: проверить переключатель на трёх глубинах. Стабильная и обычная сборки возьмутся из кэша,
мерится только новое плечо:

```bat
set "BENCHARMS=stable @stable;default;radix0 GGML_VK_TOPK_RADIX=0"
set "BENCHDEPTHS=0,65536,122880"
02-bench.bat
```

Переменная `GGML_*` или `LLAMA_*`, заданная в консоли, идёт во все плечи и в ключ.

## Значения по умолчанию

Различаются по машинам:

| Переменная | 395 | 3090 |
| --- | --- | --- |
| `EXTRA` | `-ngl 99` | `-ngl 99 -ncmoe 30` |
| `CHECKARMS` | `default`, `accurate` (f16 и f32-накопление вместо int8 coopmat) | `default` |
| `QARMS` | `default`, `nofusion`, `accurate` | `default`, `nofusion` |
| `DECARGS` | `-fit off` | `-fit off -ncmoe 48 --moe-cache auto --phase-mem --no-repack -b 4096 -ub 4096` |
| `BENCHARMS` | `stable`, `default`; на 122880 ещё `nohs`, `hsmin`, `shmem32` (поиск потери TG, см. ниже) | `stable`, `default` |
| `DECARMS` | `stable` (сервер тега), `none`, `n3` (MTP n-max 3), `auto` (`--spec-auto`) | `base`, `prompt0`, `serial`, `n2`, `serial-n2` (см. ниже) |
| `RUN_PROFILE` | 1 | 0: у llama-bench нет кэша экспертов, профиль мало говорит о сервере |
| `PROFKINDS`, `PROFARMS` | `pp tg`; `stable`, `default` | `pp`; `default` |
| `PROFDEPTH` | `0,122880` (список: каждая глубина отдельно) | 32768 |
| `BENCHCTX` | 262144: как у сервера, буферы на весь контекст | `auto`: `-c` каждой глубины = глубина + промпт, как буферы сервера с `--phase-mem`. При 262144 буферы не влезали в 24 ГБ, драйвер уносил часть в системную память, PP скакал между процессами от 115 до 430 т/с |

## Как читать результаты

Сводка каждого запуска лежит в `logs\<скрипт>-<время>\summary.txt`, рядом логи и ответы.
Пометка `k` значит, что эта же сборка измерила результат раньше.

- **02**: таблицы PP и TG, строки - глубины, столбцы - плечи; в ячейке медиана повторов и (min-max). Без прогрева первый повтор холодный, медиана его отбрасывает. В `notes` перечислены пропуски,
  падения и перепланирования буферов во время счёта (`GGML_SCHED_LOG_REALLOC`).
- **03**: `repeat` - опорное плечо ещё раз. Не 0 значит, что сборка не даёт одинаковый результат
  дважды.
  - `nofusion` - та же математика с другим округлением. KLD остальных плеч сравнивать с ним,
    а не с нулём.
  - QSA top-k на этой модели усиливает любое изменение округления: выбираются другие блоки.
    На 3090 один перенос экспертов между CPU и GPU (LFU вместо LRU) дал KLD 0.026,
    stable против текущей сборки на 395 дал 0.016.
  - `*` - отношение PPL дальше 2 сигм от 1.
- **04**: TG - сумма токенов по всем запросам на сумму времени, PP - то же по промптам, отдельно для промптов до 512 токенов и длиннее.
  - `draft accepted` - доля принятых токенов драфта.
  - Ниже по каждому плечу идут запросы, статистика спекуляции и строки `DECGREP`.
  - С выборкой (`DECSAMP` 1.0) тексты плеч расходятся, сравнивать по сумме.
- **05**: время GPU 25 самых долгих узлов последнего графа и время хоста на ubatch (`LLAMA_INPUT_TIMING`: сборка графа, входы, вызов compute). При двух плечах и больше - таблица времени GPU по типам операций рядом: где одно плечо теряет против другого. Если GPU сходится, а скорость нет, потеря на хосте.

## Текущий поиск

На 395 TG на глубине 122880 ниже stable на 2 процента: 22.48 против 22.98 (05.10), 22.68 против 23.18 (03.10).
`run-all.bat` сам проверяет, что изменилось для генерации после stable:

- `nohs` - без сшитого матмула суммы голов индексера вовсе (`GGML_VK_DISABLE_MM_HEADSUM=1`);
- `hsmin` - сшитый матмул только для промпта (`GGML_VK_HEADSUM_MIN_TOKENS=9`): шаг генерации считает каждую голову
  ядром матрица-вектор, как stable, а промпт сохраняет выигрыш. Если `hsmin` вернёт TG и не потеряет PP, это станет
  умолчанием;
- `shmem32` - с 32 КБ разделяемой памяти, как в stable (тайлы flash attention).

Заполнение входов шага генерации и так идёт в один поток, его не проверяем. Правило выбора: пара процентов TG не стоит
десятков процентов PP, поэтому изменение, которое дало PP, не откатывается, а генерация получает свой путь.

Плечо, на котором TG вернётся к stable, указывает на причину. 05-profile показывает время GPU по типам операций stable и default рядом.
Плечи убрать из `_config.bat`, когда причина найдена.

Там же:

- 05-profile снимает ubatch промпта на глубине 0 у stable и default. С этой разбивки начинается работа над промптом:
  у gufo 1628 т/с на d0 против наших около 800.
- Плечо `stable` в 04-decode печатает compute-буферы сервера stable рядом с текущими. По ним видно, что выросло:
  новая сборка при `-c 262144` падает по памяти на первой отправке команд, stable нет.

## 3090: что изменилось 05.10

- Эксперты на CPU считаются, пока GPU считает кэшированных (`GGML_SCHED_PARALLEL_CPU`), теперь по умолчанию: +3.5% TG
  без MTP и +7% с MTP на 04.10 и 05.10, ответы совпали. Плечи `serial` и `serial-n2` выключают это для сравнения.
- Промпт до 256 токенов идёт в раскладке генерации ubatch по 31 токену, кэш экспертов остаётся
  (`LLAMA_PHASE_SMALL_PROMPT`, 0 выключает). Раньше промпт в 42-85 токенов шёл в раскладке промпта около 30 т/с
  (веса экспертов CPU гонялись на GPU), а потом 0.73 с уходило на заливку 9.7 ГБ кэша. Плечо `prompt0` возвращает
  старое поведение: сравнивать столбец PP до 512 токенов и TG.
