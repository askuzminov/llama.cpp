# Проверки форка на 395 и 3090

Одни и те же скрипты на обеих машинах:

- **395** (Strix Halo, Vulkan): вся модель на GPU;
- **3090** (CUDA + i9): эксперты в RAM, горячие в кэше VRAM (`--moe-cache`).

Машина определяется по бэкенду сборки (`_config.bat`). Логика в `_qa.py` (только стандартная библиотека Python),
файлы `.bat` вызывают его. Каждый скрипт отвечает на один вопрос и ничего не сравнивает «на всякий случай»: что
нужно сравнить, задаётся явно (`QA_QARMS`, `QA_PARMS`, `CHECKARMS`).

Переменные в примерах ниже - синтаксис cmd: `set "VAR=значение"` в том же окне перед скриптом. В Git Bash `set`
переменную не задаёт (он меняет аргументы оболочки), а `;` делит строку на команды: там
`export VAR="значение"` и `./03-profile.bat`.

## Скрипты

| Скрипт | Время на 395 | Что делает |
|---|---|---|
| `00-build.bat` | | сборка в `build-win`; `00-build.bat stable` - тег `stable` в своей папке; `00-build.bat upstream` - `UPSTREAMREF` (по умолчанию master последнего слияния, `_config.bat`) в своей папке, эталон `07` |
| `01-check.bat` | ~25 мин | операции модели на устройстве против CPU (`CHECKOPS` x `CHECKARMS`), защиты памяти (веса не уходят в RAM, `QA_CHECK_GUARDS=0` - без них), юнит-тесты форка, логиты на глубинах одного контекста 32768 через путь промпта и путь генерации против эталона, восстановление частичного чекпойнта против непрерывного прогона (`QA_CHECK_CKPT=0` - без него), спекуляция сервера с головой MTP (~10 мин, `QA_CHECK_SPEC=0` - без неё) |
| `02-long.bat` | ~40 мин | весь контекст модели: логиты на глубинах до конца; один разговор до конца контекста с фактами и вопросами по ним и длинным ответом в конце; четыре разговора сразу |
| `03-profile.bat` | ~15 мин | куда уходит время на глубинах до конца: GPU по видам операций для ubatch промпта и шага генерации, шаги хоста, голова MTP |
| `04-micro.bat` | ~3 мин | индексатор QSA отдельно: LID и матмулы голов на числе токенов генерации, проверки черновика и промпта, глубины до конца |
| `05-mm.bat` | ~20 мин | плотные матмулы q8_0 промпта: путь по умолчанию и варианты тайла `mul_mm_f16reg.comp` - тесты через каждый вариант, TFLOP/s на формах модели, регистры и сброс в память у драйвера |
| `06-decode.bat` | ~6 мин на вариант | скорость генерации по видам текста: проза, проза на русском, новый код (Python, C++), правка файла (ответ переписывает файл, как агент), JSON; TG по часам сервера, черновые и принятые, варианты `QA_DARMS` рядом; `QA_DEC_TRACE` - трасса шагов черновика |
| `07-kld.bat` | ~10 мин | логиты этой сборки против сборки upstream (или точного f32-эталона, `QA_KLD_BASE=exact`) на той же модели и тексте: KLD, совпадение top-1, отношение PPL, рядом прошлый результат того же варианта с другой сборки (после слияния upstream) |
| `run-all.bat` | ~3 ч, на 3090 дольше | сборка своя и upstream, все шаги с вариантами открытых вопросов (ниже) |
| `serve.bat` | | повседневный сервер (router и `models.ini`), не проверка. `pool = on` у модели в `models.ini` делает пул из машин с этой моделью: запросы агентов делятся между ними, разговоры переезжают с состоянием, дашборд `/pool` (`POOL.md`) |
| `get-wikitext.bat` | | скачивает wikitext-2 (`PPLFILE`) |

Перед `01`-`03` остановить `serve.bat`: скрипты запускают свои процессы и не работают, пока запущен
`llama-server.exe` (он держит память GPU). Между запусками моделей скрипт ждёт, пока драйвер освободит память
прошлого процесса (`SETTLE*`), на 395 перед замером скорости ещё `COOL` секунд после сборки или долгого прогона
модели (от `COOL_RUN` секунд, 300); после короткого (вариант профиля на глубине 0) - нет.

Итог каждого запуска - в `logs/<скрипт>-<время>/summary.txt`, рядом журналы и ответы; числа каждого нового
результата добавляются в `logs/history-qa.csv`. В конце итога (12.11) - строки из журналов новых замеров этого
запуска (`from the logs of this run`): предел памяти устройства 395 и сколько держат другие процессы, отказы в памяти
устройства, перелив KV в общую память, остановка KV на пороге RAM, списки блоков QSA, слоты кеша экспертов, сколько
раз кеш промптов отдавал память, отказ fit.

`07-kld` против точного f32-эталона (`07-exact`), `02-long`; `04-micro` - только по `RUN_MICRO=1`, `05-mm` - по `RUN_MM=1`
(с 13.11; на 395 сейчас включён). После неудачной
своей сборки останавливается, после неудачи шага идёт дальше; в конце коды выхода всех шагов. Варианты
подставляются, если их нет в `_local.bat`. `RUN_BUILD`, `RUN_UPSTREAM`, `RUN_MICRO`, `RUN_CHECK`, `RUN_DECODE`,
`RUN_PROFILE`, `RUN_KLD`, `RUN_EXACT`, `RUN_LONG` = 0 в `_local.bat` убирают шаг (без `07-kld` не собирается и
upstream). Повторный запуск без изменений исходников печатает сохранённые результаты (`k`) и меряет только новые
варианты.

## Защиты памяти (01)

12.11 загрузка на 395 ушла в RAM, система ушла в своп и замерла, пока сервер не упал. С тех пор веса не уходят в
системную память без явного ключа, и 01 проверяет это на самой машине (`QA_CHECK_GUARDS`, около 3 минут):

- **395, нет места**: сервер с `GGML_VK_DEVICE_MARGIN_MIB=1048576` (ни одно выделение в памяти устройства не
  помещается) должен упасть со строкой `... MiB in use of a limit of ... MiB` (до 12.11 запасной путь UMA брал
  системную память и модель грузилась в RAM). Загрузилась - `FAIL`.
- **395, fit**: `-fit on -fitt 1048576` без `-ngl`: fit разместил бы все слои на хосте, такое размещение
  отклоняется (`refused (LLAMA_FIT_ALLOW_HOST=1 allows it)`), модель грузится как задано - все слои на GPU.
- **395, предел памяти**: строка `device memory heap 0 of ... MiB, other processes hold ... MiB of it, the driver
  budgets ... MiB: this process takes up to ... MiB` в журнале. Предел - куча минус то, что держат другие процессы
  (счётчик Windows `\GPU Adapter Memory(*)\Dedicated Usage`, как в диспетчере задач), а не 95% кучи, которые сообщает
  драйвер. Нет строки на Windows - счётчик не нашёлся, действует бюджет драйвера: `FAIL`.
  `GGML_VK_DEVICE_LIMIT=budget` возвращает бюджет. С 14.11 предел - куча минус наибольшее, что держали другие
  процессы, и минус `GGML_VK_DEVICE_RESERVE_MIB` (2048) под тех, кто возьмёт видеопамять позже (13.11: после
  переподключения RDP рабочий стол забрал своё, Windows перенесла часть сервера в системную память, своп, 19 t/s);
  строка `(... MiB more kept free for processes that take device memory later ...)`. Если другие процессы всё же
  забрали больше, сводка шага пишет «device memory the other processes took later» (с `overcommitted`, если куча
  переполнилась). Проверка руками (переподключение RDP): `serve.bat`, длинный разговор (чтобы KV вырос), отключить
  RDP на пару минут, подключиться снова, ещё один запрос; в `logs\serve-*.log` - строка предела при загрузке и,
  если другие процессы взяли больше, `other processes hold ... MiB of device memory heap 0 now`; в диспетчере задач
  «Общая память GPU» не должна расти, а «host memory is short» не должно появляться. Там же видно отдачу упругого
  KV (14.11): в простое сервера (по умолчанию после 60 с, `LLAMA_KV_TRIM_IDLE_S`) он отдаёт ячейки сверх занятых
  (`kv_elastic: idle, ... cells mapped, ... MiB given back`), а если другие процессы забрали память сверх резерва - в
  простое каждую секунду и перед батчем строка WARN `the device memory is ... MiB over its limit` и отдача всего, что
  не занято. Под нагрузкой без давления ничего не отдаётся. Если система всё же унесла память сервера в общую
  (строка `the system moved about ... MiB of the device memory of this process out of the heap`), сервер в простое
  переносит простаивающие слоты в кэш промптов (`slot N with ... tokens moved to the prompt cache`), следующий запрос
  восстанавливает разговор оттуда; когда память вернулась - `the device memory of this process is in the heap again`.
- **3090, нет места**: сервер с `-ncmoe 30` (`QA_GUARD_NCMOE`): слои экспертов на карте занимают больше 24 ГБ.
  Драйвер NVIDIA по умолчанию подложил бы под лишнее системную память (02.11 пробы шли в 25 раз медленнее, 12.11 эта
  защита загрузила 32356 МиБ на карту с 23332 свободными), а его настройку пользователь не меняет. С 12.11 выделение
  сверх свободной памяти отклоняет бэкенд (`ggml-cuda/fork/device-room-fork.inc`, FORK.md «Прочее»): строка
  `... MiB on device 0 do not fit its free memory (... MiB free of ... MiB, ... MiB kept free): refused`, загрузка
  падает - ok. Отказ самого драйвера (его fallback выключен) - тоже ok. Загрузился - `FAIL`: бэкенд не отказал
  (`GGML_CUDA_ALLOW_SYSMEM_FALLBACK=1` или сборка до 12.11). Ключи бэкенда: `GGML_CUDA_ALLOW_SYSMEM_FALLBACK=1` отдаёт
  решение драйверу, `GGML_CUDA_DEVICE_MARGIN_MIB` (0) держит свободным больше, `GGML_CUDA_ELASTIC_MARGIN_MIB` (512) -
  свободное рядом с упругим KV под пул и cuBLAS.

Результаты хранятся до новой сборки, как остальные; `FORCE=guard` - заново.

## Точность на глубине (01 и 02)

Один непрерывный контекст (01 - 32768 токенов, 02 - весь контекст модели). Пробы - последние 128 позиций перед каждой
глубиной (`QA_WINDOW`). Каждый вариант проходит контекст дважды. Сначала всё идёт батчами промпта, и логиты проб
сравниваются с эталоном (строки `prompt`); заодно вариант сохраняет свои логиты. Затем те же 128 позиций идут батчами
по 3 токена (путь генерации: неполные блоки QSA, ядра малых батчей), и логиты сравниваются с первым проходом того же
варианта (строки `decode`). Эталон - та же сборка и модель через копию upstream (`QA_REF_ENV`:
`LLAMA_UPSTREAM=qwen4exp`, его граф и память QSA) с теми же батчами: другая реализация выбора блоков, пула ключей и
маски выбранных ячеек на тех же ядрах. Побитно они не совпадают: наш выбор берёт на позициях без хвоста на один целый
блок больше (KLD 3.8e-5 при бюджете 2048 на тестовой модели). Эталон хранится в `cache/qa` до новой сборки, свои
логиты варианта - только до второго прохода. Пробы 02 идут батчами `QA_LONG_QARGS` (`-b 4096 -ub 2048`): маска эталона
на 262144 ячейках при ubatch 2048 - 1 ГиБ, при 4096 было бы 2.

Почему отдельно путь генерации: ошибка 13.10 (внимание по списку считало повторы ячеек дополнения) была видна только в
генерации. Батчи промпта, кратные 4, не дают неполных блоков, и 03-quality прежних скриптов её не видел. До 31.10 пути
брали две половины окна и оба сравнивались с эталоном; половины - разный текст, и на 395 (32768) отметка сработала на
этой разнице: на тех же позициях доля токенов выше 0.01 у обоих путей была 59%. Теперь путь генерации сравнивается с
путём промпта на тех же позициях, без эталона между ними. Mac, тестовая модель с top-k 16 (31.10): CPU - 0 на всех
пробах, Vulkan0 - 90-й процентиль 0.001-0.004 и до 4 токенов из 128 выше 0.5 (округление переворачивает почти равный
выбор блоков); сборка, выбирающая в шаге генерации вдвое меньше блоков, - 90-й процентиль 4-5.4. Реальная модель на
3090 и 395 (02.11) - 0.012-0.074 на исправной сборке, поэтому мерой служит эталон: он тоже проходит путь генерации
против своего пути промпта (таблица `reference`, ещё один прогон на сборку: около 40 с в 01, 6-8 минут в 02;
`QA_REF_DECODE=0` - без него и без отметки). Столбец `p90/ref` - 90-й процентиль строки `decode` варианта, делённый на
процентиль эталона на той же глубине.

Столбцы: KL к эталону строки (медиана, 90-й процентиль, максимум), доля токенов с KL выше 0.01, число токенов выше
0.5, совпадение top-1, средняя разница NLL. Отдельные токены с большим KL бывают и у исправной сборки: при близких
оценках блоков любая разница округления (даже порядок сложения в f32) меняет выбор top-k или маршрут экспертов.
Систематическая ошибка поднимает медиану, процентиль и долю. Отметки: `DECODE DIFFERS` - 90-й процентиль KL пути
генерации к пути промпта выше, чем у эталона, больше чем в `QA_DECODE_RATIO` (2) раза; `PROMPT DIFFERS` (04.11) - 90-й
процентиль KL пути промпта к эталону выше шума эталона на этой машине (его путь генерации к его пути промпта, столбец
p90/ref) больше чем в `QA_PROMPT_RATIO` (2) раза: на 3090 02.11 путь промпта был 0.75-1.26 этого шума; `LOW TOP1` -
совпадение top-1 пути промпта с эталоном ниже 85%. Без прогона пути генерации эталона (`QA_REF_DECODE=0`) шума нет, и
первые две отметки не ставятся. Любая отметка - код выхода 1. На реальной модели против копии upstream (31.10, 395 и
3090) шум реализаций - медиана KL до 0.015, 90-й процентиль до 0.11, top-1 84-100%.

Пробы логитов смотрят только на саму модель (`llama-quality-fork` не строит черновики): голова MTP, отбор черновиков
по p/q и откаты в них не попадают. Поэтому 01 запускает ещё сервер, как `serve.bat` (`SPECDRAFT`, `QA_SPEC`), и
спрашивает его с черновиками и без (поле запроса форка `"speculative.n_max": 0`):

- temperature 0, `QA_SPEC_PROMPTS` (4) частей корпуса по `QA_SPEC_GREEDY` (64) токенов: токены совпадают до первого
  другого, там разница log p первого и второго токена без черновиков. Ошибка проверки черновиков или отката
  расходится и там, где модель уверена: `SPEC GREEDY DIFFERS`, если разница больше `QA_SPEC_MARGIN` (1.0). Тонкую
  ошибку это не ловит: черновик расходится с моделью как раз там, где она не уверена. До первого другого токена
  контекст один, поэтому распределения двух путей сравнимы в каждой позиции (12.11, `QA_SPEC_PROBS` лучших у обоих):
  столбец «with drafts» - разница log p тех же двух токенов в пути проверки (меньше 0 - он берёт второй), «shift
  before» - наибольшее изменение этой разницы на токенах до расхождения (округление двух путей). Токен с черновиками,
  который не первый в своём же распределении, при temperature 0 - ошибка принятия при любом округлении:
  `SPEC NOT GREEDY`. На 395 12.11 (`--spec-auto` с потолком 7, проверка до 8 токенов) часть 0 разошлась на токене 5 с
  разницей 1.35; 09.11 при потолке 3 - тот же токен с разницей 0.51;
- temperature 1, в цепочке только температура, `QA_SPEC_TOKENS` (2048) токенов каждой части: для каждого токена
  сервер отдаёт вероятности, из которых он взят (`QA_SPEC_PROBS` (20) лучших, остальное одной корзиной), и
  рандомизированное преобразование PIT должно дать равномерное распределение. Хи-квадрат по 20 корзинам
  рандомизированного (форма) и z-тест среднего PIT по середине `lo + p/2` (сдвиг; у него среднее ровно 0.5 под
  распределением каждой позиции, дисперсия считается точно по тому же распределению, случайного числа в нём нет):
  `SPEC SAMPLING DIFFERS`, если хоть одно p со спекуляцией ниже `QA_SPEC_ALPHA`
  (1e-4) или вышел токен вне распределения; то же без черновиков - `SPEC PROBE DIFFERS` (не держится сама проба);
  `NO DRAFTS` - черновиков не было. На Mac (stories15M_MOE с черновиком stories15M q4_0, 8000 токенов) проба
  поймала все три поломки отбора из ревью 04.11: остаток из p вместо norm(p - q)+, переставленные p_x и q_x, одно
  случайное число на принятие и остаток; на 2000 токенах - две из трёх.

Вероятности по токенам (13.11): llama-server пишет запись `completion_probabilities` только для токена, после
которого текст - целый UTF-8 (символ из байтовых кусков - тире, буква с диакритикой, CJK - даёт запись лишь
последнему куску), а `tokens` (`return_tokens`) перечисляет все. До 13.11 проба склеивала два списка по порядку, и
после первого такого символа каждый токен оценивался распределением следующей позиции: среднее PIT без черновиков
0.502-0.522 во всех 11 прогонах на обеих машинах, разница в части temperature 0 бралась не с той позиции, если такой
символ был до расхождения (столбец «shift before» сравнивал позиции двух ответов между собой и оставался верным). На
Mac (DeepSeek-R1-Distill-Qwen-7B Q4_K_M, словарь 152K, 5.9K токенов при temperature 1): склейка по порядку - среднее
0.5100 (p 0.0076), по записям - 0.4979 (p 0.58). Теперь каждая запись идёт со своим токеном (`id`), у токенов без
записи распределения нет (`aligned_probs`). `QA_SPEC_ARMS` (`name VAR=value ...;...`, по умолчанию `default`) -
варианты пробы, сервер каждого со своим окружением (на 395 13.11 - `planes2 GGML_VK_MMVQ_PLANES=2`).

Среднее PIT (13.11, вечер): до этого z-тест среднего шёл по рандомизированному преобразованию, а случайные числа брались из
`random.Random(1000)` в каждом прогоне. Первые 1500-1600 значений этого потока в среднем 0.516-0.517 (z до 2.4), и
каждый прогон обеих машин получал один и тот же сдвиг, около 0.015, умноженного на вероятность выбранного токена: среднее
без черновиков 0.511-0.518 во всех прогонах 13.11 (17 из 17 прогонов ноября выше 0.5), у `spec` 16:57 на 3090 0.522
(p 0.004). Симуляция (распределения по 200 токенов, 1600 токенов на прогон): при верной выборке тест по середине даёт
p < 0.05 в 4.5% прогонов и p < 0.01 в 1.0%, рандомизированный с тем же зерном - p < 0.05 в 8.5%; выборка при
температуре 1.1 против отданной 1.0 сдвигает среднее на +0.04 и ловится в 20 прогонах из 20 при p < 1e-4. Столбец
`scored` - токены с записью вероятностей (из `tokens`); identity пробы получила `"pit": 2`, старые результаты
считаются заново.

Принятие черновиков на заданном тексте (`QA_CHECK_FORCED=1`, по умолчанию выключено; 09.11): грамматика из одного
литерала заставляет модель при temperature 0 написать продолжение части корпуса, голова MTP черновит без грамматики,
поэтому все варианты черновят по одним и тем же токенам из одних и тех же контекстов - сравнение ядер, через которые
идут черновики. Принятие свободных ответов зависит от текста (03 и проба спекуляции дали одному ядру оба знака) и от
длины черновика: `--spec-auto` берёт её из измеренной стоимости проверки, быстрее проверка - длиннее черновики и
меньше доля принятых. Поэтому длина фиксирована: `QA_FORCED_SPEC` (по умолчанию `--spec-draft-n-min 3
--spec-draft-n-max 3 --spec-draft-p-min 0`) вместо `QA_SPEC`. `QA_FORCED_PROMPTS` (16) частей: `QA_FORCED_CTX`
(3000) символов контекста и `QA_FORCED_CHARS` (1500) заданного текста, сервер с `QA_FORCED_N_CTX` (8192). Строка на
часть: токены, совпал ли ответ с текстом (`FORCED TEXT DIFFERS`, если нет), черновых и принятых, TG (с грамматикой на
CPU). На Mac (stories15M_MOE с черновиком stories15M, 6 частей) счётчики повторяются от запуска к запуску до единицы.

Между ходами разговора сервер восстанавливает частичный чекпойнт (рекуррентное состояние; внимание откатывается через
`seq_rm`) и читает дальше. ctest проверяет это только на сгенерированных моделях, поэтому 01 запускает
`test-checkpoint-partial` с моделью, как её грузит сервер (`EXTRA`, `LOADMODE`, `DECARGS`; ревью 04.11):
`QA_CKPT_TOKENS` (8192) токенов корпуса читаются двумя половинами с чекпойнтом после первой, затем чекпойнт
восстанавливается и вторая половина читается заново. Логиты последнего токена сравниваются с непрерывным прогоном:
тест требует тот же top-1 и разницу не больше 1e-2, итог пишет `bit for bit` или разницу. Вторая половина лежит за
бюджетом выбора QSA (513 блоков по 4 токена) и идёт разреженным путём, одним батчем промпта. Путь генерации после
восстановления тест не проходит. Mac (04.11): 8 моделей ctest и qwen4exp-moe с top-k 16 на 256 токенах - разница 0
на CPU, Vulkan0 и Vulkan1.

Варианты для сравнения: `QA_QARMS="default;pool32 LLAMA_QSA_POOL_F32=1"` - каждый против того же эталона. Отдельная
таблица показывает, на скольких пробах каждый вариант дал NLL default бит в бит (равные логиты дают равный NLL) и
первую пробу, где нет. Второй default с непрочитанной переменной (`again LLAMA_QA_AGAIN=1`; в ключ результата идут
только переменные `GGML_`, `LLAMA_`, `CUDA_`, `HIP_`, `OMP_`) показывает, повторяет ли себя прогон: до 01.11
radix-select выбора блоков на Vulkan складывал выбор атомарно, и два одинаковых прогона расходились с первого ubatch
4096 токенов; radix-select CUDA - до 02.11, с первой пробы после ubatch больше чем на 1024 блока KV (3090, 16256 из
32768). Оба теперь пишут выбор по возрастанию индекса, равные k-му значению - с наименьшего
(`GGML_VK_TOPK_RADIX_STABLE`, `GGML_CUDA_TOPK_RADIX_STABLE`; 0 - как в upstream).

## Длинный разговор (02)

## Против upstream (07)

Эталон 01 и 02 - та же сборка через копию графа upstream (`LLAMA_UPSTREAM=qwen4exp`): ядра форка (f16reg, int8
coopmat, фьюжены, radix top-k) в нём те же, и их отличие от upstream там не видно. `07-kld.bat` сравнивает со сборкой
самого upstream: `00-build.bat upstream` собирает `UPSTREAMREF` (по умолчанию master последнего слияния из `_config.bat`) в
`build-upstream-src` / `build-upstream` (`UPSTREAMSRC`, `UPSTREAMBUILD`), затем `llama-perplexity` upstream пишет
логиты `QA_KLD_CHUNKS` (2) кусков по `QA_KLD_CTX` (8192) токенов `PPLFILE` (сравнивается вторая половина каждого, как
в perplexity; файл эталона около 4 ГБ при словаре 248320, лежит в `cache/qa` до новой сборки upstream), и каждый
вариант `QA_KARMS` сравнивается с ними. По умолчанию `fork` (эта сборка как есть) и `upstream @upstream` (upstream ещё
раз: шум эталона, 0, когда upstream повторяет себя бит в бит). Свой вариант: `QA_KARMS="fork;noq8
GGML_VK_DISABLE_INTEGER_DOT_PRODUCT=1 GGML_VK_INT_COOPMAT=0;upgraph LLAMA_UPSTREAM=qwen4exp"`. Аргументы модели те же,
что у проб (`LOADMODE`, `EXTRA`), батч - `-b` = контекст, `-ub` `QA_KLD_UB` (4096, на CUDA 8192), лишнее -
`QA_KLD_ARGS`, окружение эталона - `QA_KLD_BASE_ENV`.

Столбцы: PPL варианта, его отношение к PPL, которую upstream напечатал при записи эталона (выше 1 - хуже upstream;
PPL(base) самой perplexity не берётся: она восстановлена из 16-битных log p с нижним порогом и у токенов ниже порога
занижена), средний, медианный, 99-й процентиль и максимум KLD, совпадение top-1. Последний столбец - прошлый результат
того же варианта на этой машине с другой сборки (`history-qa.csv`): после слияния upstream - `00-build.bat`,
`00-build.bat upstream`, затем `07`. Рост KLD или отношения PPL против прошлого результата значит, что после слияния
форк дальше от upstream, чем был до него. С 12.11 `07` проверяет, что сборка upstream - это `UPSTREAMREF`: сборка
другого коммита (прошлое слияние, старые файлы после неудачной сборки нового) - ошибка с подсказкой
`00-build.bat upstream`. Значения форка, которых upstream не знает, идут ему в его форме (`UPSTREAM_VALUES` в
`_qa.py`): `-lzm dio` (строки через кеш строк форка) - `-lzm on` (строки по требованию из отображения файла). Без
этого 12.11 `07` против upstream упал на обеих машинах: `error while handling argument "-lzm": invalid value`.

Точный эталон (12.11): `QA_KLD_BASE=exact` пишет логиты этой же сборкой, где все матмулы считаются в f32 (Vulkan: без
int8, без f16-шейдеров и coopmat, пути f16 форка выключены, список - `KLD_EXACT_ENV` в `_qa.py`). Тогда KLD каждого
варианта - цена его собственных 8- и 16-битных активаций и порядка сумм, а не расстояние до upstream (у upstream на RDNA3
свои q8_1-активации). На CUDA режима f32 пока нет, `07` тогда пропускается. `QA_ARM_UB=<n>` в варианте задаёт его ubatch:
1-8 токенов запускают ядра декода (мат-векторы, матвек экспертов форка), которых батч промпта не касается. Пример для
395 - путь промпта, путь декода на 4 токенах и он же на f32-матвеках:
`QA_KLD_BASE=exact QA_KARMS="prompt;decode4 QA_ARM_UB=4;decode4f32 QA_ARM_UB=4 GGML_VK_DISABLE_MMVQ=1 GGML_VK_MMV_ID_FORK=0"`.
Декод на 4 токенах идёт медленно: 16K токенов по 4 - около 4000 графов.

`"QA_ARM_ARGS=<аргументы>"` в варианте 07 (в кавычках целиком, 12.11) - аргументы только этого варианта после
аргументов модели; более позднее значение опции побеждает. Так раскладывается разница с upstream: 12.11 на 395 PPL
форка 1.9460, его точного f32-эталона 1.9456, upstream 1.9270 (KLD 0.033), то есть разница не от наших 8- и 16-битных
приближений. На Mac на тестовых qwen4exp (CPU и Vulkan, QSA и маршрутизация 32 экспертов включены, несколько ubatch,
строки PLE через кеш строк и через отображение) форк и upstream расходятся не больше чем на KLD 2e-6, обходной путь
маски top-k upstream (без слитой операции, как на Vulkan 395) совпадает со слитым. Плечи, которые раскладывают разницу
на 395: граф upstream в этой сборке (`copy`), строки PLE как у upstream (`lzmon`), ключи пулов QSA в f32 (`pool32`),
внимание по маске вместо списка (`nolist`), без отбора QSA у нас и у upstream (`dense`, `updense`). Итог на 395
12.11: `lzmon` и `pool32` побитно как `fork` (1.9460), `nolist` 1.9467, `copy` 1.9382, `dense` 1.9438, `updense`
1.9277 при upstream 1.9270. То есть PLE, пул и список ни при чём, отбор QSA тоже (без него разрыв 0.84%); граф форка -
около 40% разрыва, остальное есть и с графом upstream в этой сборке (бэкенд или общая инфраструктура, на тестовых
моделях Mac не видно). Дальше на 395 - граф upstream без отбора и слияния Vulkan выключенными

13.11: на CUDA upstream 1.9472, граф upstream в нашей сборке - тот же побитно (KLD 0, top-1 100%), форк 1.9364; наш

## Микробенчмарк (04)

`test-micro-fork` строит подграф индексатора так, как его строит граф qwen4exp, и гоняет его целиком на устройстве
машины (`CHECKDEVICE`): `test-backend-ops perf` повторяет только последний узел и слитый матмул голов не меряет.
Случаи: `lid` - `LIGHTNING_INDEXER` (на Vulkan внутри идёт слитый матмул голов при любом числе токенов, с 31.10;
`GGML_VK_LID_HEADSUM=0` - всегда шейдер индексатора), `headsum` - четыре матмула, `relu`, сумма и смещение, как граф Vulkan (`MUL_MAT_HEADSUM`),
`batched` - один матмул по головам, как граф других бэкендов. Входы общие (фиксированное зерно), все блоки видны.
Строка: блоки (кэш / 4), токены, мкс на граф (медиана), TFLOP/s, ГБ/с, копий графа в одном запуске, наибольшая разница
к первому случаю относительно его наибольшей оценки. `QA_MICRO_ARGS` - аргументы (`-c`, `-t`, `-b`, `--ms`), `QA_MARMS` -
варианты, например `QA_MARMS="default;scalar GGML_VK_LID_HEADSUM=0"`.

## Плотный матмул (05)

С 13.11 05 мерит и проверку черновиков: `QA_MM_N=8` (1, 2 или 4) берёт формы плотных q8_0 одного шага проверки
qwen4exp (perf-список форка, голова LM и hc down из f16 тоже), последняя строка - мс плотных q8_0 одной проверки по
счёту профиля 03 (13.11). Варианты - окружение пути: int8-матвек (с ночи 13.11 на RDNA3 только с
`GGML_VK_MM_F16REG_VERIFY=0`: без него умолчание - тайл проверки и две плоскости q8_0), две плоскости
(`GGML_VK_MM_F16REG_VERIFY=0 GGML_VK_MMVQ_PLANES=2 GGML_VK_MMVQ_PLANES_TYPES=q8_0`), тайл проверки
`GGML_VK_MM_F16REG_VERIFY=<тайл>` с `GGML_VK_MM_F16REG_VERIFY_MIN_M=1` (все формы через тайл, по умолчанию от 1024
строк). Из run-all - по `RUN_MM=1`.

`05-mm.bat`: плотные матмулы q8_0 ubatch промпта на устройстве (`CHECKDEVICE`) - путь по умолчанию (int8 coopmat) и
варианты `mul_mm_f16reg.comp` (`GGML_VK_MM_F16REG`, с 07.11, по умолчанию выключен). Ядро по схеме плотного GEMM
gufo: f16 WMMA, веса q8_0 распаковываются в f16, суммы в f32 по всему K, следующий шаг K грузится, пока считается
текущий. Вариант `<r|l><строк>x<токенов>/<m>x<n>[n|h]`: строк и токенов на подгруппу из 32 (кратно 16), m x n подгрупп
в рабочей группе; `r` - коды распаковываются в регистрах прямо во фрагмент A (как у экспертов), `l` - в f16 по пути в
shared memory, фрагменты A грузятся оттуда; последняя буква - тайл B следующего шага не держится в регистрах (`n`,
каждый шаг читает свой) или держится в f16 (`h`), без буквы - в f32, как прочитан. `r32x64/4x2` - тайл 128 строк x
128 токенов из 8 подгрупп по 32 x 64. На подгруппу не больше 64 строк x 128 токенов и 16 фрагментов сумм (суммы в
шейдере - 4 x 8 фрагментов с константными индексами, с 08.11; до того 4 x 4).

Для каждого варианта сначала тесты `MUL_MAT` q8_0 против CPU, все через вариант (`GGML_VK_MM_F16REG_MIN_N=1`,
`_MIN_M=1`, `_MIN_K=1`; `via` - сколько матмулов он взял; на Mac проверен только эмулированный путь, coopmat-путь
впервые проверяется здесь). Вариант, который устройство не взяло (не хватило shared memory, нет coopmat), помечен `off`
и не меряется. Затем `test-backend-ops perf` на формах q8_0 qwen4exp при `QA_MM_N` токенах (4096) с порогами по
умолчанию (формы с M < 512 или K < 1024 идут int8-путём): TFLOP/s по формам (`*` - лучший на форме), последняя строка -
мс всех плотных матмулов q8_0 одного ubatch 4096 по счёту профиля 31.10 (у int8 там ~1450 мс). Короткий K этот тест не
судит: на 10240 x 320 он дал ядру 1.34 мс, а в модели (профиль 03) было 2.43 против 1.49 у int8. Внизу статистика конвейеров от драйвера: VGPR, scratch (сброс регистров в память, такой вариант медленный), LDS.
`QA_MMARMS` - варианты (`имя VAR=значение ...;...`), по умолчанию `int8` (`GGML_VK_MM_F16REG=0`: с 08.11 на RDNA3 по
умолчанию `r16x64/8x1`) и варианты третьего прогона (`MM_VARIANTS` в `_qa.py`). Первый прогон 07.11 (`logs/395/mm-20261107-201543`): лучший `r16x64/8x1`, у тайлов 64x64 на подгруппу
scratch 544-640 байт. Второй (`mm-20261107-220919`): без B в f32 на регистрах у 64x64 всё равно не меньше 544 байт
(16 сумм по 32 байта и ещё 32), `r16x64/8x1` 1305 мс против 1464. Третий: суммы в шейдере названы константами, а не

Третий (`mm-20261107-225950`): влезают (scratch 0, VGPR 225-255, кроме 64x64/2x2), но не обгоняют: `r16x64/8x1` 1303

## Что не запускается повторно

Результат хранится в `cache/` под описанием того, что его дало: исходники сборки (`00-build.bat` записывает их
хэш), аргументы, окружение `GGML_*`/`LLAMA_*`/`CUDA_*`, файлы модели, входные данные, машина. Если описание не
изменилось, скрипт печатает сохранённый результат с пометкой `k`. `FORCE=1` - всё заново, `FORCE=<regex>` - совпавшие
части (например `FORCE=long-chat`).

## Повседневный сервер (`models.ini`)

Что из замеров стоит держать в `models.ini`, который запускает `serve.bat`.

**395**, в секции модели (нужна сборка не старше a6cca899a, 06.10):

```ini
override-tensor = blk\.4[4-7]\.ffn_.*_exps=Vulkan0_Shared
```

Эксперты слоёв 44-47 (6.5 ГБ) уходят в общую память GPU (16 ГБ на 395), GPU читает их на месте. По замерам 06.10 это
не стоит ничего ни в PP, ни в TG, а на устройстве при `-c 262144 -ub 4096` освобождается 6.5 ГБ запаса. K/V туда не
класть (`LLAMA_KV_SHARED=1`): на глубине 122880 это стоит 2.6% TG и 4.6% PP. `-ub` оставить 4096: 2048 стоит 5% PP
без выигрыша в TG.

**3090** - не подходит: `Vulkan0_Shared` есть только в сборке Vulkan, с CUDA сервер не запустится
(`unknown buffer type`). Эксперты 3090 и так лежат в RAM (`-ncmoe 48 --moe-cache auto --phase-mem`). С 05.10
по умолчанию включено и не требует ключей: эксперты на CPU считаются параллельно с кэшированными на GPU
(`GGML_SCHED_PARALLEL_CPU`), промпт до 192 токенов идёт без сброса кэша экспертов (`LLAMA_PHASE_SMALL_PROMPT`).
С 14.10 `_config.bat` ставит на 3090 `GGML_OP_OFFLOAD_MIN_BATCH=128`: эксперты из RAM заливаются на GPU только для
ubatch от 128 токенов, короче считаются на CPU ubatch по 127. Ходы чата в 111-197 токенов на глубине 29K стали 2.09 с
вместо 2.57, TG и длинные ходы не хуже. Для своего запуска сервера переменную нужно задать самому.
`GGML_SCHED_PREFETCH` (с 14.10 по умолчанию 3, `0` - выкл): эксперты сплита заливаются на GPU вторым потоком CUDA,
пока считается сплит на три раньше, а не после синхронизации в его начале; ходы ~3.8K +25%, короткие ходы и TG те же
(`FORK.md`).

Потолок черновика `--spec-auto` с 09.11 по умолчанию 7 (было 3): на 395 код +15%, проза -3.7% (раздел 06). На 3090
12.10 выигрывал 3 (эксперты на CPU: проверка дорожает с каждым токеном), после этого его не мерили: в секции модели
`models.ini` на 3090

```ini
spec-draft-n-max = 3
```

`_config.bat` на 3090 ставит то же прогонам (`QA_SPEC=--spec-auto --spec-draft-n-max 3`). Состояния отката при 7 -
на ~0.45 ГиБ больше, чем при 3.
