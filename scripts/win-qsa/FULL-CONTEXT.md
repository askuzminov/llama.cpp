# Проверки на полной длине контекста

`09-full-context.bat` проверяет текущую сборку на длине из `<architecture>.context_length` в GGUF. Например, для модели с контекстом 262144 это 262144, без сокращения до 16K. Скрипт не меняет `models.ini`.

## Запуск

В `_local.bat` должны быть заданы `MODEL`, `SPECDRAFT` и настройки размещения весов для этой машины, как для остальных скриптов. Запустить `00-build.bat`: он также собирает новый `llama-quality-fork.exe`.

Указать длинные естественные тексты. Каждый файл должен содержать хотя бы `context_length + 1` токенов **этой модели**. Короткий файл вызывает ошибку; скрипт не повторяет его и не сокращает контекст.

```bat
set "FULL_CORPORA=wiki=C:\data\wiki.txt;ru=C:\data\russian.txt;code=C:\data\code.txt"
```

Без `FULL_CORPORA` используется `PPLFILE`. Серверные сценарии используют первый корпус как наполнитель. Проверка NLL проходит по каждому корпусу отдельно. Текст на одном языке не подтверждает качество на других языках или в коде.

Сначала можно проверить настройки без загрузки весов и инференса:

```bat
set "FULL_DRY_RUN=1"
09-full-context.bat
set "FULL_DRY_RUN="
09-full-context.bat
```

Это команды в `cmd.exe` из папки `scripts\win-qsa`. Для постоянных настроек перенести `set` в `_local.bat`. Если `FULL_DRY_RUN` задан там, убрать его перед настоящим прогоном. План и оценка размера эталона находятся в `manifest.json`.

Полный набор дорогой: 8 вариантов сервера x 2 значения параллельности x 4 задачи x 3 seed x холодный/повторный запрос, плюс фиксированная генерация, качество, кеш и профиль. При длинном префилле это может занять несколько суток. Каждый запрос сохраняет длину; незаметного перехода на короткие тесты нет. Для запуска частями:

```bat
set "FULL_STAGES=quality"
09-full-context.bat
set "FULL_STAGES=server"
09-full-context.bat
set "FULL_STAGES=mixed cache profile"
09-full-context.bat
```

На время измерений остановить повседневный сервер самостоятельно. Скрипт запускает собственные процессы на `127.0.0.1:8098` и завершает только их. Производственный каталог дискового кеша не используется: для тестов создаются отдельные каталоги внутри журнала запуска.

## Что измеряется

**Численная точность.** Эталон использует те же веса и текущую сборку с `LLAMA_HC_F16=0`, `LLAMA_QSA_POOL_F32=1`, `GGML_VK_F16ACC=0`. Это сравнение оптимизаций с более консервативным вычислением, а не независимое доказательство правильности всего форка. Сравниваются повтор эталона, текущие значения по умолчанию, HC в F32 и QSA pool в F32. `FULL_F16ACC=1` добавляет диагностический вариант с F16 accumulation.

Для каждого варианта последовательно обрабатываются все `C` токенов одного непрерывного контекста, без сбросов между окнами. Метрики снимаются на последних 128 позициях перед глубинами 4096, 32768, 65536, 131072, 200000 и `C` (лишние глубины объединяются). Последний входной токен стоит на позиции `C-1` и предсказывает токен `C`. Поэтому корпусу нужен ещё один токен. Сохраняются FP32-логиты эталона; в памяти держится не более `FULL_ROWS` выходов за батч, по умолчанию 32.

Отчёт содержит NLL, **выборочную PPL**, KL, total variation, совпадение top-1 и максимальное изменение логита. Есть общий результат и результаты по глубинам. Это не PPL по всем токенам: полный префилл проходит целиком, оценивается выборка предсказаний. Для оценки каждой позиции есть `FULL_DENSE=1`; оценка размера эталона в плане учитывает это. При большом словаре такой файл может занять сотни гигабайт. В dense-режиме сохраняются отдельные проверки последних 128 позиций у контрольных глубин, чтобы общее среднее не скрывало хвост.

Логиты снимаются для одной последовательности. Четыре слота проверяются серверными заданиями, без вычисления полного KL между четырьмя одновременно резидентными контекстами. Набор рассчитан на текст; качество изображений/mmproj требует отдельных контрольных данных.

Порог ухудшения NLL по умолчанию равен нулю. Приближённый 95% интервал вычисляется парным блочным bootstrap; соседние токены не считаются независимыми. `PASS_SAMPLED_NLL` относится только к проверенным данным и окнам. `IDENTICAL_AT_PROBES` означает точное совпадение снятых логитов. `INCONCLUSIVE` означает недостаточность данных. Отдельная регрессия на хвосте не скрывается хорошим общим средним. Повтор эталона помогает увидеть недетерминизм вычислений: при его изменении появляется `REPEAT_VARIATION`, а положительный статистический вывод для следующего варианта понижается до `INCONCLUSIVE_CONTROL`. Эти интервалы не гарантируют качество на любых запросах.

**Сервер и MTP.** Отдельные запуски с `-np 1` и `-np 4`: без спекуляции, auto, фиксированные максимумы draft 1/2/3, окна MTP 8K/16K/32K. При подборе фиксированной длины отключается ограничитель `LLAMA_SPEC_DRAFT_BY_SLOTS`, иначе вариант 3 при четырёх слотах мог бы фактически использовать 2. Draft остаётся probabilistic с проверкой target. Без файла MTP соответствующие варианты получают `NOT_TESTED`.

Запросы занимают `C - FULL_NGEN - 1` токенов с учётом шаблона. Оставлен запас под ответ; контекст не превышается и context shift отключён. Проверяются записи на разных глубинах, вопрос на русском, выполнение простой функции и настоящий tool call через `/v1/chat/completions`. Для tools считается результат серверного парсера `tool_calls`, а не похожий JSON в обычном тексте. Ответы оцениваются по известным значениям. Для обычных задач применяется шаблон модели через `/apply-template`; tools используют тот же шаблон в chat API.

Функциональные ответы заканчиваются естественно. Обрезанный по лимиту ответ не считается успешным; повторяющийся хвост помечается эвристикой по токенам. Отдельная серия с `ignore_eos=true` генерирует ровно `FULL_NGEN` токенов для сопоставимой скорости; её продолжение после EOS не используется как проверка качества. Сохраняются aggregate tokens/s по настенному времени, TTFT, ITL p95 по поступившим токенам и p95 между событиями SSE. При MTP несколько токенов могут прийти одним событием; интервалы внутри такого пакета равны нулю, размер пакета записывается отдельно. Tools проверяются без стрима, поэтому их TTFT не оценивается.

У общего KV размер `C`, как в исходной конфигурации. Четыре полных контекста одновременно обычно требуют больше памяти; сервер может ставить запросы в очередь. Это измерение обслуживания четырёх полных запросов с общей ёмкостью `C`, а не обещание четырёх одновременно резидентных контекстов. Скрипт не делит длину запроса на четыре и не увеличивает память до `4*C` без указания. Ошибка выделения памяти остаётся ошибкой.

Холодные запросы отключают reuse через `cache_prompt=false`, повторные включают его. `warm_requested` не гарантирует попадание в кеш: фактически использованные токены записаны в `cached_n` из `timings.cache_n`. Для p4 длинные запросы могут вытеснить состояния друг друга.

**Префилл.** Бюджеты 256/1024/2048/4096/0 при `LLAMA_PREFILL_EXCLUSIVE=0`. Три запроса сначала начинают генерацию, затем приходит четвёртый длинный префилл. Их длины `C/8` и `C/2` специально оставляют место всем в общем KV; четыре полных контекста проверяют очередь и не подходят для изолированного измерения чередования. Если генерация успела закончиться, результат получает `NO_OVERLAP`. Сравнивать задержки такого прогона как корректный тест чередования нельзя.

**Дисковый кеш.** Сравниваются шаги записи 0/8192/32768 в отдельных пустых каталогах. История постепенно дорастает до конца контекста; после каждого шага снимаются размер файлов и фактический объём/время записи из журнала write-behind. Перед замером файлов ожидается завершение временных записей и стабилизация каталога. Затем сервер перезапускается: проверяются фактическое попадание в кеш и совпадение greedy-токенов с последним ответом до перезапуска, а также с независимым холодным запуском. Если восстановление совпало, а холодный префилл отличается от поэтапного, результат `INCONCLUSIVE_PREFILL_PATH`: это повод исследовать различие путей вычисления, без автоматического вывода о порче дискового кеша или отсутствии потери качества. Это проверка одного GGUF; общий лимит между разными моделями и корректность при аварийном отключении питания этим прогоном не доказываются.

**Профиль.** Запрос у полного конца контекста с `LLAMA_INPUT_TIMING`, `GGML_TIMELINE`, `LLAMA_MOE_CACHE_STATS`, Vulkan per-op logger либо CUDA op timing. Для захвата timeline применяется нестриминговый chat-запрос и диапазон `LLAMA_TRACE_REQUESTS=1:1`; отсутствие файла профиля вызывает ошибку. Журналы помогают найти ожидания хоста, ввод экспертов и вычисления GPU. Профилирование само меняет скорость, его цифры не используются для выбора победителя. Автоматической атрибуции каждой паузы к дисковому I/O нет; для углублённого исследования CUDA остаётся `07-trace.bat` с Nsight Systems.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `FULL_CTX` | native GGUF | Только для явно укороченного smoke-прогона; `full_native_context=false` |
| `FULL_STAGES` | `quality server mixed cache profile` | Выбор этапов через пробел |
| `FULL_WINDOW` | `128` | Размер окна снятия логитов |
| `FULL_ROWS` | `32` | Максимум выходов с логитами в одном батче, 1..128 |
| `FULL_QARGS` | `-b 16384 -ub 4096` Vulkan/CPU, `-ub 8192` CUDA | Размеры батчей численной проверки; размещение весов берётся из `EXTRA` |
| `FULL_DENSE` | `0` | Снимать логиты каждой позиции; большой эталон |
| `FULL_QARMS` | repeat/default/hc32/pool32 | Список вариантов через `;`, синтаксис как у `QARMS`, текущая сборка |
| `FULL_F16ACC` | `0` | Добавить диагностический F16ACC в численную проверку |
| `FULL_NLL_MARGIN` | `0` | Допустимое ухудшение среднего NLL; положительное значение ослабляет критерий |
| `FULL_ARMS` | none/auto/n1/n2/n3/w8192/w16384/w32768 | Серверные варианты через `;`, синтаксис `DECARMS` |
| `FULL_PAR` | `1 4` | Число слотов в отдельных запусках сервера |
| `FULL_TASKS` | `retrieve ru code tool` | Функциональные сценарии |
| `FULL_REPEATS` | `1` | Повторы с разными фактами и идентификаторами документов |
| `FULL_SEEDS` | `1 2 3` | Seed для семплирования и замеров |
| `FULL_SAMP` | `1.0 20 0.95` | temperature, top-k, top-p |
| `FULL_NGEN` | `512` | Резерв ответа и длина фиксированной генерации |
| `FULL_BUDGETS` | `256 1024 2048 4096 0` | Бюджеты смешанного префилла |
| `FULL_MIX_NGEN` | `1024` | Генерация в смешанном тесте, ограничена также `C/32` |
| `FULL_CACHE_STEPS` | `0 8192 32768` | Минимум/шаг записи кеша |
| `FULL_CACHE_TURNS` | `4` | Число добавлений к истории перед перезапуском |
| `FULL_CACHE_GROW` | `2048`, не более `C/16` | Токенов в одном добавлении к истории |
| `FULL_CACHE_MIB` | `50000` | Общий бюджет тестового каталога кеша |
| `FULL_PORT` | `8098` | Порт собственных серверов |
| `FULL_TIMEOUT` | `7200` | Таймаут одного HTTP-запроса, секунды |

Численная проверка на CUDA использует размещение из `EXTRA`, как `03-quality`; серверные этапы дополнительно используют `DECARGS` с expert cache/phase memory. Это разные пути исполнения. Успех численной проверки не заменяет серверные проверки CUDA. Размер контекста, число слотов, путь кеша и context shift в серверных тестах задаются самим тестом после `DECARGS`.

## Результаты и повторный запуск

В `logs/full-context-*` лежат `manifest.json`, `results.json`, `comparisons.json`, `summary.txt`, ответы и сырые журналы. В `comparisons.json` скорость сравнивается с `none` при том же числе слотов. Если базовая модель сама не решила задачу, сравнение качества остаётся `INCONCLUSIVE`. Потеря успешного базового ответа хотя бы в одном парном случае отмечается как `TASK_REGRESSION`, даже при одинаковой общей доле успехов.

Токены, эталоны и завершённые численные/серверные/смешанные прогоны переиспользуются из `cache/`. Ключи включают бинарники, библиотеки, модель со всеми частями, корпус, параметры, окружение и версию драйвера скрипта. `FORCE=1` повторяет замеры; `FORCE=full-server-auto-p4` повторяет совпадающий замер. Метаданные, кеш с перезапуском и профиль выполняются снова. Результат большого варианта сохраняется после завершения этого варианта; прерванный вариант запускается заново.

Код выхода 1 означает техническую ошибку или обнаруженную регрессию. Код 0 означает завершение выбранных этапов; он **не означает** доказанное отсутствие потери качества. Пропущенные варианты, неполный набор корпусов, `INCONCLUSIVE`, `NO_OVERLAP` и ограничения простых контрольных задач видны в отчёте. Скрипт не выбирает и не применяет настройки автоматически.

Проверка самого инструментария:

```bat
python scripts\win-qsa\test_full.py
set "LLAMA_QUALITY_TEST_BIN=build-win\bin\Release\llama-quality-fork.exe"
set "LLAMA_QUALITY_TEST_MODEL=C:\models\small-model.gguf"
python scripts\win-qsa\test_full.py
```

Эти команды запускаются из корня репозитория. Для native smoke-тестов лучше маленькая обычная текстовая модель: проверяются точное self-сравнение, конец контекста, короткий корпус, несовпадение токенов, обрезанный эталон и NaN. Это проверки инструмента, а не результаты качества большой рабочей модели.
